# 项目二 service-agent 里程碑 M2 技术设计方案（审计 + 两层权限过滤）

> 本文是「智能工单系统」**项目二：service-agent** 的**第二个里程碑（M2）**设计依据，承接 `设计理念/start.md`（M1 骨架 + 只读问答）。
> 写法沿用 M1：既写「怎么做」，也写**「为什么这么设计」与「我们没选什么」**；落地清单与验证方式见 §五、§七。
> 文中「项目一」= `backend/WorkOrderSystem`（`com.rj`，端口 10001，Service-Boot **4.1.1**）；「agent」= `Agent/AgentWorkOrder`（`com.agentworkorder`，端口 **10002**）。
> **本文只做设计，不含实现代码。**

## 一、文档定位

### 1.1 范围

M1 已经证明「自然语言 → 工具调用 → 项目一 → 自然语言」这条主干能通（见 M1 §12）。M2 在这条主干上叠两块**正交的加固**：

| 目标 | 一句话 | 交付物 |
|---|---|---|
| **目标一：工具调用审计** | 每次工具调用留一条可追责的流水 | 表 `agent_tool_call_log` + 实体/Mapper/审计服务 + 埋点 |
| **目标二：两层权限过滤** | 用户没权限的工具，模型**根本看不到** | 调 `/tool/user/info` 取 `perms` → 按工具所需的权限码**收敛工具清单** |

交付物清单（都是 **agent 侧**改动，项目一**零改动**）：

1. agent 引入 MySQL + MyBatis-Plus，建库 `agent_workorder`、建表 `agent_tool_call_log`；
2. `GET /tool/user/info` 的 agent 客户端方法 + 带 TTL 的 perms 缓存；
3. 「工具 → 权限码」注册表 + 按 perms 过滤 `ToolCallback` 的逻辑；
4. 对 M1 的 `SpringAiLlmClient` / `MockLlmClient` / `WorkOrderTools` 的改造。

### 1.2 边界（不在 M2 范围）

| 不做 | 放到 | 原因 |
|---|---|---|
| 写工具（改状态、派单）的审计与判权 | M4 | 项目一写接口目前仍只是可运行 demo，agent 无从对接 |
| 把审计表做成「可查询的前端页面 / 报表」 | 视需要 | M2 只保证**写进表**；查询是后续的事 |
| 把 perms 缓存换成 Redis | M5 | M2 用进程内 TTL 缓存即可；接口一致，后续替换不动业务 |
| RAG 知识库 | M3 | 与审计、判权完全正交 |
| 审计的「模型侧 token 用量 / 成本」 | M5 | 需要模型返回 usage，属于成本治理，独立做 |

### 1.3 一句话总览

> **给工具调用装上「黑匣子」（每次都记一条到 agent 自建的审计表），并给工具装一道「可见性闸门」（用项目一 `/tool/user/info` 返回的 `perms`，把用户无权使用的工具从交给模型的清单里摘掉）。**

一层纪律仍然贯穿：**agent 不发明权限**——用户有什么权限，一律以项目一 `/tool/user/info` 的 `perms` 为准；agent 只负责「按这个清单收敛工具可见性」，不参与任何权限规则的计算。

## 二、前置事实核对（项目一契约，实测引用）

> 下列事实已对照项目一源码核对，M2 直接依赖它们。**与 M1 文档描述一致，此处精确化到字段级**。

### 2.1 `/tool/user/info` 的返回结构（目标二的输入）

- 端点：`GET /tool/user/info`（`com.rj.controller.tool.ToolUserController`），**无参数**，返回 `com.rj.model.vo.UserVO`。
- 关键字段（`UserVO.java`）：

```java
private Long userId;
private String username;
private String realName;
private List<String> roles;   // 如 ["HANDLER"]
private List<String> perms;   // 如 ["workorder:process","workorder:query"]  ← 注意字段名是 perms
```

**要点：** 权限字段名是 **`perms`**（不是 `permissions`），类型是**扁平的 `List<String>`**（权限码字符串列表），**不嵌套**。这是 M2 过滤器唯一需要读的字段。

### 2.2 权限码全表（工具判权依据）

来自 `src/main/resources/db/data.sql` 的 `permission` 表（id 1..10），共 10 个：

```
workorder:create    workorder:modify   workorder:withdraw   workorder:accept   workorder:query
workorder:review    workorder:dispatch workorder:process    workorder:transfer user:manage
```

角色→权限映射（`role_permission`）：`ADMIN` 拥有全部 10 个；`SUBMITTER/REVIEWER/DISPATCHER/HANDLER` 均含 **`workorder:query`**。

### 2.3 只读工具的权限要求（项目一已经判过一次）

`com.rj.controller.tool.ToolWorkOrderController`：

| 端点 | 方法 | 所需权限 |
|---|---|---|
| `GET /tool/workorder/list` | `list(current,size,status,orderType,keyword)` | `@RequiresPermission("workorder:query")` |
| `GET /tool/workorder/{id}` | `detail(id)` | `@RequiresPermission("workorder:query")` |

- 列表参数：`current`(默认1) / `size`(默认10，后端**静默封顶 50**) / `status` / `orderType` / `keyword`；返回 `PageResult<WorkOrderVO>`（`records,total,current,size`）。
- 详情返回 `WorkOrderDetailVO`。
- `@RequiresPermission` 语义是 **AND**（`UserAuth.hasAll` 用 `containsAll`），**不能表达「任一即可」**——这解释了为什么写接口 `PUT /tool/workorder/{id}/status` 没有注解。M2 的只读工具只涉及单权限码，不受此限。

### 2.4 错误体与 HTTP 状态（审计要识别成功/失败）

- `/tool/**` 的**业务错误**返回精简体 `{"code":<int>,"message":"<str>"}`（`ToolErrorVO`，record），且 **HTTP 状态恒为 200**（`ToolExceptionHandler` 类上无 `@ResponseStatus`）。
- `code` 取自 `ResultCode`：`400 参数错误 / 401 未登录 / 403 无权限 / 404 数据不存在 / 500 系统异常`。
- **成功体是裸 JSON，不套 `code`。**

> ⚠️ 因此 **agent 无法用 HTTP 状态判断成败，必须看 body**。M2 的「调用成功/失败」判定规则见 §3.5。

### 2.5 agent 侧的现状（M1 产物）

`Agent/AgentWorkOrder/src/main/java/com/agentworkorder/`：`llm/{LlmClient,SpringAiLlmClient,MockLlmClient}`、`client/WorkOrderToolClient`、`tool/WorkOrderTools`、`controller/AgentChatController`、`config/{LlmProperties,WorkOrderProperties,ChatMemoryConfig}`。Spring AI 版本 **1.1.2**，Boot **4.1.1**。

## 三、目标一：工具调用审计表 `agent_tool_call_log`

### 3.1 为什么放在 agent 自建，而不是项目一

M1 的纪律是「agent 不碰数据库」。M2 **有意识地修订**它，限定为：**agent 只新建「只属于自己的、非业务的」数据；一切业务事实仍以项目一为准**。审计表恰好满足这个限定：

| 维度 | 只有 agent 知道 | 项目一能看到 |
|---|---|---|
| `sessionId`（哪轮会话） | ✅ | ✗ |
| 用户**原始自然语言**问题 | ✅ | ✗ |
| 模型命中/未命中的工具、参数 | ✅ | 只看到最终 HTTP 调用 |
| `provider`（mock/openai）、模型名 | ✅ | ✗ |
| 调用**结果体** | ✅ | ✅（它就是产出方） |

审计的核心诉求是「**可追责**」——要能回答「谁、在哪轮对话里、因为什么、调了什么工具、拿到了什么」。这份上下文**几乎全在 agent 手里**，项目一只能看到半截。故：

- **agent 自建库/表**（本方案）；
- 项目一**零改动**（它是已完工的成品，不该为 agent 的可观测性返工）。

### 3.2 表设计

库：**独立数据库 `agent_workorder`**（与项目一的 `work_order_system` 分开，边界清晰；同实例不同库即可）。DDL 风格**严格对齐项目一**（见 `db/schema.sql` 头注释：MySQL 8.x / InnoDB / utf8mb4 / 反引号 / `DATETIME` / 表级 `COMMENT`）。

```sql
-- Agent 侧审计表：只增不改，无逻辑删除、无 update_time
DROP TABLE IF EXISTS `agent_tool_call_log`;
CREATE TABLE `agent_tool_call_log` (
  `id`             BIGINT        NOT NULL AUTO_INCREMENT COMMENT '主键',
  `trace_id`       VARCHAR(64)   NOT NULL                COMMENT '一次对话请求的关联id(agent生成,同一轮的所有工具调用共享)',
  `session_id`     VARCHAR(64)   NOT NULL                COMMENT '会话id',
  `user_id`        BIGINT        NULL                    COMMENT '用户id(取自 /tool/user/info)',
  `username`       VARCHAR(64)   NULL                    COMMENT '用户名',
  `tool_name`      VARCHAR(64)   NOT NULL                COMMENT '工具名:listWorkOrders / queryWorkOrder',
  `tool_args`      VARCHAR(1000) NULL                    COMMENT '工具入参JSON',
  `call_status`    VARCHAR(16)   NOT NULL                COMMENT '调用结果:SUCCESS / ERROR',
  `result_code`    INT           NULL                    COMMENT '项目一错误体的code(失败时);成功为NULL',
  `result_excerpt` VARCHAR(512)  NULL                    COMMENT '返回体摘要(截断,不存全量)',
  `result_length`  INT           NULL                    COMMENT '返回体原始长度(字节)',
  `latency_ms`     BIGINT        NULL                    COMMENT '调用耗时(毫秒)',
  `error_message`  VARCHAR(512)  NULL                    COMMENT '异常信息(失败时)',
  `provider`       VARCHAR(32)   NULL                    COMMENT '模型提供方:mock / openai',
  `create_time`    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (`id`),
  KEY `idx_session`      (`session_id`),
  KEY `idx_user_time`    (`user_id`, `create_time`),
  KEY `idx_tool_time`    (`tool_name`, `create_time`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT='Agent 工具调用审计日志(只增不改)';
```

设计要点：

- **只增不改**：审计日志天然 append-only，**不加** `deleted`/`update_time`（对齐项目一「逻辑删除只用于可变主数据」的原则）。
- **三个索引**对应三种追责视角：按会话、按人（+时间）、按工具（+时间）。
- **`trace_id`** 让「一轮对话里的多次工具调用」可聚合成一条链。

### 3.3 实体 / Mapper / 审计服务

风格对齐项目一（**无 BaseEntity**；`@TableName` + `@TableId(IdType.AUTO)`；camelCase→snake_case 自动映射）：

```java
@Data
@TableName("agent_tool_call_log")
public class AgentToolCallLog {
    @TableId(type = IdType.AUTO)
    private Long id;
    private String traceId;
    private String sessionId;
    private Long userId;
    private String username;
    private String toolName;
    private String toolArgs;
    private String callStatus;   // SUCCESS / ERROR
    private Integer resultCode;
    private String resultExcerpt;
    private Integer resultLength;
    private Long latencyMs;
    private String errorMessage;
    private String provider;
    private LocalDateTime createTime;
}
```

- Mapper：`interface AgentToolCallLogMapper extends BaseMapper<AgentToolCallLog> {}`，用 `@MapperScan("com.agentworkorder.audit.mapper")` 注册。
- 服务：`ToolCallAuditor`（`@Service`），对外只有一个方法，内部**吞掉一切异常**（见 §3.6）：

```java
void record(AuditContext ctx, String toolName, Map<String,Object> args,
            String body, Integer resultCode, Throwable error, long latencyMs, String provider);
```

### 3.4 埋点位置：放在 `@Tool` 方法边界

**在哪一层埋点**有三种候选，选**工具方法边界**：

| 候选 | 能拿到的信息 | 结论 |
|---|---|---|
| `WorkOrderToolClient`（HTTP 层） | 只有 URL/参数/body，**没有 sessionId / 用户 / provider** | ✗ |
| `@Tool` 方法（`WorkOrderTools`） | 全部（ToolContext 里有 auth/session/trace/provider） | ✅ **选它** |
| Spring AI 的 `ToolCallback` 装饰器 / Advisor | 可以，但要吃透 Spring AI 内部 API，收益不划算 | 留作将来 |

实现上给 `WorkOrderTools` 加一个**私有模板方法**，两个 `@Tool` 方法各缩成一行：

```java
private String audited(String toolName, Map<String,Object> args, ToolContext ctx, Supplier<String> call) {
    long start = System.nanoTime();
    try {
        String body = call.get();
        auditor.record(ctx, toolName, args, body, ToolResult.inspectCode(body), null, elapsedMs(start), providerOf(ctx));
        return body;
    } catch (RuntimeException e) {
        auditor.record(ctx, toolName, args, null, null, e, elapsedMs(start), providerOf(ctx));
        throw e;                       // 审计只旁观，不改变原有异常传播
    }
}
```

> ✅ **顺带好处**：`MockLlmClient` 是**直接调用** `WorkOrderTools` 方法的（M1 如此设计，为的是无 key 也能验证链路），所以 **mock 与 openai 两条路径都会被同一次埋点覆盖**，无需分别处理。

### 3.5 成功 / 失败怎么判定

因为项目一恒返回 200（§2.4），判定规则必须看 body：

- **成功与业务失败**：把 body 解析成 JSON，若**顶层同时存在 `code` 与 `message` 两个字段** → 判为 `ERROR`，`result_code = code`（`ToolErrorVO` 的确切形状，误判概率最低）；否则 `SUCCESS`。
- **传输层异常**（项目一没起、超时、`RestClient` 抛 `ResourceAccessException`）→ `ERROR`，`error_message = e.getMessage()`。
- 两种失败**都要记**——「谁在什么情况下被拒」正是审计最关心的。

> ⚠️ **Jackson 版本坑**：agent 是 **Boot 4.1.1 → Jackson 3**，包名是 `tools.jackson.*`（`tools.jackson.databind.json.JsonMapper`），**不是** `com.fasterxml.jackson.*`。照抄 Boot 3 的老代码会引入第二个 ObjectMapper。解析 body 用 Boot 自动配置的 Jackson 3 即可。

### 3.6 审计绝不能拖垮主流程

**硬性要求**：审计写库失败（表不存在、连接池满、字段超长…）**不能**让对话失败。做法：

- `ToolCallAuditor.record(...)` 内部 `try { mapper.insert(...) } catch (Exception e) { log.warn("审计写入失败: {}", ...); }`——**只告警、不抛出**；
- `tool_args` / `result_excerpt` / `error_message` 写入前**截断**到列宽内（§3.2 的 `VARCHAR` 上限），避免 `Data too long` 把一条审计变成异常；
- 提供一个开关 `agent.audit.enabled`（默认 `true`），关掉时埋点直接短路（用于压测）。

### 3.7 存什么、不存什么（脱敏）

| 字段 | 存 | 理由 |
|---|---|---|
| `tool_args` | **完整** | 只读工具的入参只有 `status/orderType/keyword/id`，无敏感信息 |
| `result_excerpt` | **截断**（默认 ≤512 字符） | 返回体可能很大且含业务明细（PII）；审计要的是「调过、大概返回了啥」，不是数据副本。另存 `result_length` 保留「有多大」的信号 |
| `result_code` | 完整 | 追责关键：是 403 还是 404 |

## 四、目标二：两层权限过滤（工具可见性）

### 4.1 「两层」分别是什么

| 层 | 在哪 | 做什么 | M2 是否新增 |
|---|---|---|---|
| **Layer A（准入门）** | 项目一 `LoginInterceptor` | 校验 JWT 合法 → 加载 `UserAuth(roles+perms)` → 方法级 `@RequiresPermission("workorder:query")` | ❌ 已有 |
| **Layer B（可见性门）** | agent | 调 `/tool/user/info` 取 `perms` → **不把用户无权使用的工具交给模型** | ✅ 新增 |

**为什么两层都要**：Layer A 是**兜底**——即使 Layer B 失效（代码漏洞 / 未来新路径漏注册），无权限的调用打到项目一也会被 403 挡住，绝不会泄露数据。Layer B 是**体验与成本**——让模型**看不见**碰不到的工具，降低误调用与 token 浪费，也让模型不会「幻觉」出一个它根本不该用的工具。

### 4.2 工具 → 权限码映射（注册表）

```java
// ToolPermissionRegistry（agent 侧，静态表）
"listWorkOrders"  -> "workorder:query"
"queryWorkOrder"  -> "workorder:query"
// M4 接入写工具时在此追加：changeStatus 需按动作分别要求 review/dispatch/process/accept/withdraw 之一
```

> 只读工具只涉及单一权限码，不触碰项目一「`@RequiresPermission` 只能 AND」的局限（§2.3）。M4 的写工具若遇「任一动作即可」的语义，**必须在 agent 侧按动作拆开**，不能指望项目一那条注解。

### 4.3 拿 `perms`：调 `/tool/user/info` + TTL 缓存

新增 `WorkOrderToolClient.getUserInfo(String authToken)`（与 M1 一致，**返回原始 String**）；新增 `PermService`：

```java
UserPerms load(String authToken, String traceId);
// UserPerms = record(Long userId, String username, Set<String> permCodes)
```

- **缓存**：进程内 `ConcurrentHashMap<String, Cached>`，key = token 的 SHA-256（不落明文 token），TTL 默认 **60 秒**（`agent.perm.cache-ttl-seconds`）。理由：每轮对话都调一次 `/tool/user/info` 是纯浪费（项目一自己已用 Redis 缓存 `UserAuth`），但缓存太长会让「改权限后不生效」的窗口变大。
- **解析**：body 若含 `code`+`message`（401/403 等）→ 视为**匿名**（空 perms）；否则用 Jackson 3 解析出 `userId/username/perms`。
- **将来**：M5 把这张进程内缓存换成 Redis，`PermService` 接口不变。

### 4.4 按 perms 过滤工具（Spring AI 1.1.2 的具体做法，已实测）

M1 是用 `ChatClient.Builder.defaultTools(workOrderTools)` **在构建期**把工具一次注册。**要在运行期按用户过滤，必须改成「每请求注册」**：

1. 构建期（一次）：把所有工具方法编成 `ToolCallback[]` 并缓存——

```java
// 实测可用的 API（Spring AI 1.1.2，org.springframework.ai.tool.method）
ToolCallback[] all = MethodToolCallbackProvider.builder()
        .toolObjects(workOrderTools)      // 对象级；两个方法都在同一个 @Component 里
        .build()
        .getToolCallbacks();
// 工具名：cb.getToolDefinition().name()  →  "listWorkOrders" / "queryWorkOrder"
```

2. 每请求：按 `perms` 过滤，再用 `.toolCallbacks(...)` 注册可见子集——

```java
Set<String> permCodes = permService.load(authToken).permCodes();
List<ToolCallback> visible = Arrays.stream(all)
        .filter(cb -> permCodes.contains(registry.requiredPerm(cb.getToolDefinition().name())))
        .toList();

chatClient.prompt()
        .user(userMessage)
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, sessionId))
        .toolCallbacks(visible)                                   // ← 只把有权用的交给模型
        .toolContext(ToolContextKeys.build(authToken, sessionId, traceId, userPerms, provider))
        .stream().content();
```

> ⚠️ 改动连带：`SpringAiLlmClient` 的构造器里**去掉 `defaultTools(...)`**（否则会把全量工具又加回去，过滤白做）；`MockLlmClient` 也要**照同一套 perms → 可见工具**的逻辑走，保证两条路径行为一致。

### 4.5 fail-closed（默认拒绝）

当 `perms` 拿不到时，**不注册任何工具**，让模型/ mock 明确回答「未登录或无权查询工单」，而不是「先放行再寄望项目一拦」。触发场景：

- 请求没带 `Authorization`；
- token 失效 → `/tool/user/info` 返回 `{code:401,...}`；
- 项目一不可达 → `PermService` 捕获异常，降级为空 perms。

这仍符合「agent 不发明权限」——agent 只是**只信项目一给的清单**，给不出清单就不放行。

## 七、端到端验证（M2）

前置：项目一（10001）与 MySQL 已起；agent 的 `db/schema.sql` 已执行（建库 `agent_workorder` + 表 `agent_tool_call_log`）。

1. **启动与基线**：agent 以 `provider=mock` 起在 10002，`contextLoads` 通过（新增 DatabaseSource / Mapper 装配无误）。
2. **审计落表**：admin 登录取 JWT → 打 `/api/agent/chat` → `SELECT * FROM agent_tool_call_log`，应见 **1 条 `listWorkOrders`**：`call_status='SUCCESS'`、`user_id` 非空、`latency_ms>0`、`session_id` 正确、`provider='mock'`。
3. **失败也记**：停掉项目一 → 再打一次 → 表里新增 **1 条 `ERROR`**，`error_message` 含连接失败信息，**且 SSE 仍正常返回**（审计/工具异常没拖垮主流程）。恢复项目一。
4. **权限过滤（重点，注意种子数据的坑）**：
   > ⚠️ 项目一种子里 **5 个角色全都带 `workorder:query`**，所以**用现成账号测不出「工具被隐藏」**。要验证 Layer B，必须制造「有身份但无 `workorder:query`」或「无有效身份」两种情况：
   - **(a) 未带 `Authorization`** → `PermService` 拿不到 perms（fail-closed）→ 模型/ mock 回答「未登录或无权查询」；审计表若产生行，`call_status` 不应为 SUCCESS。
   - **(b) 造一个无角色用户**（`user` 里插一条、`user_role` **不**插映射）→ 登录后 `perms` 为空 → 两个工具都不可见。
   - **(c) 临时改种子**：从 `role_permission` 删掉某角色到 `workorder:query` 的映射 → 该角色登录后工具隐藏。**测完记得恢复**。
5. **缓存 TTL**：把 `agent.perm.cache-ttl-seconds` 设为 `0`（或重启）再重复步骤 4，确认过滤即时生效，排除「缓存导致测不出」的假象。
6. **fail-closed 反例**：把 token 换成垃圾串 → `/tool/user/info` 返回 `{code:401}` → agent 视为匿名 → 无工具；直接打项目一 `/tool/workorder/list` 也应 403/401（证明 Layer A 仍在）。

**通过标准**：审计表的行数、`call_status`、`user_id`、`provider` 与上面每步预期一致；权限过滤在「无 perms」时**一个工具都不下发给模型**。

## 九、我们没选什么

| 备选 | 为什么不选 |
|---|---|
| 审计落**项目一**（复用其 MySQL） | 项目一只能看到半截（没有 sessionId / 用户原话 / 模型信息），可追责性差；且要动一个已完工的成品，风险与收益不匹配（§3.1） |
| 审计**只写日志不建表** | 违背 M1 §11 明确的「审计表」表述，且不便按用户/工具/时间查询与追责（§1.2） |
| **只在 `@Tool` 内判权**，不隐藏工具 | 文档要求的是**可见性收敛**；只判权会让模型「看得见、调得着、被拒绝」，浪费 token 且易诱发幻觉。**不过仍建议在 `@Tool` 内保留一层兜底判权**（防御纵深），只是不作为主策略 |
| 用 agent 把 JWT 解开、自己算权限 | 直接违反「agent 不发明权限」；权限的唯一事实来源是项目一 `/tool/user/info` 的 `perms`（§4.1、§4.5） |
| 把 perms 也塞进会话记忆 | 记忆是「给模型的对话历史」，权限是「运行时闸门」，两者生命周期不同；混在一起会导致改权限后要等记忆过期才生效 |
