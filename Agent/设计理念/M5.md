## 一、文档定位

### 1.1 范围

M1 把「自然语言 → 工具调用 → 项目一 → 自然语言」这条主干跑通，M2 给工具装上审计与可见性闸门，M3 让模型懂业务规则，M4 打开受控的写能力。M5 不再加新业务能力，只做**「让这套东西在真实环境里不轻易倒」**的五件事：

| 目标 | 一句话 | 主要交付物 |
|---|---|---|
| **目标一：Redis 会话记忆** | 重启不丢、多实例共享 | 自写 `RedisChatMemoryRepository`（Spring AI 1.1.2 没有官方 Redis 实现） |
| **目标二：进程内状态外置** | perms 缓存、写确认令牌搬进 Redis | `PermCache` / `PendingWriteStore` 两个端口 + Redis 实现 |
| **目标三：SSE 协议收口** | 客户端能明确知道「正常结束 / 出错 / 还活着」 | `token` / `done` / `error` / 心跳注释 + 超时 + 断连处理 |
| **目标四：降级与熔断** | 下游挂了，快速失败、给人话，不拖垮整条对话 | 约 100 行的 `CircuitBreaker` + `ResilienceGuard`，包住项目一 / LLM / RAG |
| **目标五：可运维** | 审计表不无限膨胀，出问题能看指标 | 审计保留清理 + 补 `create_time` 索引 + Actuator 指标 / 健康检查 |

交付完成后，agent 的**进程内**只剩「每轮写次数」和 mock 的演示状态；真正需要跨请求、跨实例的数据都在 Redis / MySQL 里。

### 1.2 边界（不在 M5 范围）

| 不做 | 放到 | 原因 |
|---|---|---|
| 分布式链路追踪（Micrometer Tracing / SkyWalking） | 以后 | 当前 `traceId` 已能串起「一轮对话的所有工具调用」，先够用；引入全链路追踪是另一套基础设施 |
| Sentinel 控制台 / 集群流控 / 热点参数限流 | 附录 B 可选 | M5 只需要「下游挂了别一直打」，不需要一整套流控平台；详见 §7.2 |
| Redis 主从 / 哨兵 / Cluster 高可用 | 运维 | 本文只假设单机 Redis；key 设计与 TTL 对将来的高可用是兼容的 |
| 把 SSE 改成消息队列异步消费 | 以后 | 当前是「一次请求一条流」，MQ 会改变交互模型，收益与成本不匹配 |
| 会话历史查询页面 / 会话列表 | 以后 | M5 只保证记忆可用；「给用户看历史」是产品功能 |
| RAG Rerank / 混合检索 / Query 改写 | 以后 | 与韧性正交；M5 只给检索加熔断与超时 |
| 新增 `POST /api/agent/chat` | 以后 | 当前 GET + query 有 URL 长度限制；改协议要前端一起动，M5 不混进来 |
| 创建工单 / 重新提交 / 批量写 | M4.1 或永远不做 | 沿用 M4 的边界 |
| 前端「点按钮才确认」的强确认通道 | 前端迭代 | 令牌仍不是用户同意的证明，M4 §7.1 的结论不变 |
| 工具结果缓存（Redis 缓存工单列表） | 不做 | 工单数据有时效性与数据范围，缓存会制造「看到旧数据 / 越权数据」的风险 |
| 把 JWT 存进 Redis | 不做 | 只需要存 token 的 SHA-256 做缓存 key；明文 token 不落任何存储 |

### 1.3 一句话总览

> **把「进程内三张表」（会话记忆、perms 缓存、写确认令牌）搬进 Redis；给 SSE 一个能收尾的协议（token / done / error / 心跳）；给项目一、LLM、RAG 三个外部依赖装一个约 100 行、能读懂的熔断器；再给审计表加一把按时间清理的扫帚。读可以降级，写必须 fail-closed，降级绝不伪装成成功。**

### 1.4 三条贯穿全文的纪律

1. **降级不是假成功。** 下游不可用时，工具返回明确的 `{"code":503,...}`，模型如实说「服务暂不可用」；绝不能返回一个空列表让模型以为「你没有工单」。
2. **写路径 fail-closed。** 权限拿不到、令牌存储不可用、状态不确定时，**不写**。读路径可以退化为「少查一点」，写路径只能退化为「不写」。
3. **进程内状态不是事实来源。** 会话、权限、令牌都可能在另一台实例上；需要跨请求共享的东西，一律放 Redis；需要追责的东西，一律放 MySQL 审计表。

### 2.3 Redis 现状

- 依赖已在 `pom.xml`；`application.yaml` 里已经配了 `spring.data.redis.*`，`database=5`，与项目一的 `database=4` 分开，避免键空间互相污染。
- **业务代码目前一次都没用过 Redis**；`spring.data.redis.timeout: 10000` 是「Redis 故障时每条命令最多等 10 秒」——M5 必须下调（§4.3），否则「降级」会变成「每个请求卡 10 秒」。
- Lettuce 连接是**懒建立**的：Redis 没起，应用通常仍能启动；真正发命令时才报错。所以 Redis 不能出现在「启动必须成功」的路径里。

### 2.4 SSE 现状

当前 `AgentChatController` 的核心只有一行：

```java
return llmClient.stream(sessionId, message, authorization)
        .map(token -> ServerSentEvent.builder(token).build());
```

它有三个问题：

1. **没有心跳**：模型思考超过网关空闲超时（常见 60s），连接会被 Nginx / 负载均衡掐断，客户端只看到「流突然没了」。
2. **没有终止事件**：客户端无法区分「模型说完了」和「连接断了」。
3. **错误直接穿透**：LLM 抛异常时，Reactor 的错误会终止流，Spring MVC 可能已经提交了 200 响应头，客户端只能看到连接异常，拿不到可读原因。

### 2.5 韧性现状

| 位置 | 现在做了什么 | 缺什么 |
|---|---|---|
| `WorkOrderToolClient` | connect 2s / read 10s；异常直接抛 | 没有熔断；项目一挂了，每次请求都要等超时 |
| `KnowledgeRetriever` | 统一 `catch`，返回 `{"code":500,...}` | 没有熔断；Milvus 挂了，每次检索都等一次失败 |
| `ToolCallAuditor` | `try/catch` 吞异常，只告警 | 没有语句超时；MySQL 慢时可能拖住工具调用 |
| `SpringAiLlmClient` | 直接调 `ChatClient` | 没有熔断、没有首 token / 空闲超时 |
| Redis | 未使用 | 没有降级策略 |

### 2.6 已核对：Spring AI 1.1.2 的会话记忆 API

M5 的会话记忆方案依赖下面这个接口（已按 1.1.2 Javadoc 核对）：

```java
public interface ChatMemoryRepository {
    List<String> findConversationIds();
    List<Message> findByConversationId(String conversationId);
    void saveAll(String conversationId, List<Message> messages);   // 全量替换
    void deleteByConversationId(String conversationId);
}
```

两个关键结论：

1. **`ChatMemory` / `MessageWindowChatMemory` 本身不用换。** `MessageWindowChatMemory` 负责「只保留最近 N 条」，它把真正的读写委托给 `ChatMemoryRepository`。所以 M5 只需要写一个 Redis 版 Repository，业务代码（`SpringAiLlmClient`、`MessageChatMemoryAdvisor`）不动。
2. **Spring AI 1.1.2 没有官方 Redis 版 Repository。** 目前本地 `.m2` 里没有 `spring-ai-*-chat-memory-redis` 构件；官方 `RedisChatMemoryRepository` 出现在 2.0.0-M2 的文档里。所以不要指望「引一个 starter 就完事」，自己写一个约 100 行的适配器反而更稳、更可控。

补充事实：

- `MessageType` 的取值是 `USER / ASSISTANT / SYSTEM / TOOL`。
- `Message` 接口有 `getText()` 与 `getMessageType()`。
- 用 `UserMessage` / `AssistantMessage` / `SystemMessage` 的 `String` 构造器即可还原纯文本消息。

### 2.7 一个必须修的安全问题：sessionId 不能单独当记忆键

M1–M4 的记忆键只有 `sessionId`，而 `sessionId` 是**客户端自己传的**。这意味着：

```
用户 A 用 sessionId=s1 聊过「我要离职，帮我查…」
用户 B 也传 sessionId=s1
→ 如果记忆共享，B 的下一轮请求会把 A 的对话历史注入 prompt
```

进程内单实例时，这个问题被「同一时刻只有一个用户」掩盖了；M5 一旦上 Redis 多实例，风险会被放大。M5 的处理：

1. **记忆键加用户维度**：`conversationId = userId + ":" + sessionId`；匿名用户用 `anon:` 前缀。
2. **controller 校验 sessionId 字符集与长度**：只允许 `[A-Za-z0-9_-]{1,64}`，防止奇怪字符造成 key 注入或超长 key。
3. 匿名用户仍可能共用同一个 `anon:s1`，但匿名用户本来就查不到任何业务数据；文档里如实说明。

## 三、总体设计

### 3.1 目标架构

```
                         ┌──────────────────────────┐
       浏览器 / 客户端 ──▶│  agent 实例 A / B（10002）│
          SSE v2         │  Controller → LlmClient  │
                         │       │                  │
                         │       ├── 工具可见性（perms）
                         │       ├── @Tool ─────────┼──▶ 项目一 /tool/**（熔断器 project-one）
                         │       ├── searchKnowledge┼──▶ Milvus + embedding（熔断器 rag）
                         │       └── LLM 流 ────────┼──▶ DeepSeek / OpenAI 兼容（熔断器 llm）
                         └───────┬──────────┬───────┘
                                 │          │
                    ┌────────────▼──┐  ┌────▼─────────────────┐
                    │ Redis（db5）  │  │ MySQL（work_order_    │
                    │ 记忆 / perms  │  │ system.agent_tool_    │
                    │ / 写令牌      │  │ call_log 审计）       │
                    └───────────────┘  └──────────────────────┘
```

### 3.2 三条主要数据流

**读问答（M1–M3 主干，M5 加韧性）**

```
GET /chat
  → 校验 sessionId / message
  → PermService.load（先 Redis 缓存，miss 再打项目一；项目一故障时匿名 fail-closed）
  → 按 perms 过滤 ToolCallback
  → ChatClient.stream
      ├─ listWorkOrders / queryWorkOrder → 项目一（熔断 + 超时 + 错误体）
      ├─ searchKnowledge               → RAG（熔断 + 超时 + 错误体）
      └─ 记忆读写                      → Redis（故障时退化为「无记忆」）
  → SSE：token… + heartbeat… + done / error
```

**写确认（M4 主干，M5 把令牌搬进 Redis）**

```
第一次调用（无令牌）
  → 读工单（项目一，熔断）→ 预览 → 签发令牌 → Redis（TTL 300s）
用户确认
  → 任意实例收到请求
  → 新鲜权限校验（loadFresh，fail-closed）
  → Redis GETDEL 令牌（原子一次性）
  → WriteGuard（本实例本轮写次数）
  → PUT /tool/workorder/{id}/status
```

**降级（故障时）**

```
项目一挂 → 工具返回 {"code":503} → 模型说「工单服务暂不可用」；对话不中断
LLM 挂   → SSE 发 event:error    → 客户端显示可读错误；连接正常收尾
RAG 挂   → 检索工具返回错误体    → 模型仍能查工单
Redis 挂 → 记忆退化为无记忆；perms 退化为直查；写令牌 fail-closed（不写）
MySQL 挂 → 审计跳过、只告警      → 对话与写操作照常
```

### 3.3 Redis key 设计（先定契约，再写代码）

| key | 类型 | value | TTL | 写入方 | Redis 挂了会怎样 |
|---|---|---|---|---|---|
| `agent:chat:memory:{userId}:{sessionId}` | String | 会话快照 JSON（版本 + 消息列表） | 7 天，每次保存刷新 | `RedisChatMemoryRepository` | 读不到 → 当无记忆；写失败 → 只告警，本轮对话照常 |
| `agent:perm:{sha256(token)}` | String | `UserPerms` JSON | 60 秒 | `RedisPermCache` | 缓存 miss → 直查项目一；项目一也挂 → 匿名（fail-closed） |
| `agent:write:pending:{token}` | String | `PendingWrite` JSON | 300 秒 | `RedisPendingWriteStore` | 签发 / 消费失败 → 503，**不写**（fail-closed） |

设计要点：

- **所有 key 必须带 TTL**。没有 TTL 的 key 在 Redis 里就是内存泄漏；`write:pending` 更是安全敏感数据。
- **key 里不放明文 JWT**。perms 缓存用 SHA-256；写令牌本身就是随机串。
- **key 前缀可配置**，方便多环境共用一套 Redis 时隔离（比如 `agent:dev:` / `agent:prod:`）。
- **不要在 key 里放中文 / 空格 / 超长 sessionId**；controller 已经校验。

### 3.4 降级矩阵（谁挂了，用户看到什么）

| 依赖 | 读工具 | 写工具 | 会话记忆 | 权限 | SSE | 用户看到 |
|---|---|---|---|---|---|---|
| 项目一不可达 | 返回 `503` 错误体 | 预览失败（不签令牌）/ 确认返回「结果未知」 | 正常 | 拿不到 perms → 匿名，工具不可见 | 正常收尾 | 「工单服务暂不可用」或「未登录/无权」 |
| LLM 不可达 | — | — | 正常 | 正常 | `event:error` | 「模型服务暂时不可用，请稍后重试」 |
| Embedding / Milvus 不可达 | `searchKnowledge` 返回 `503` | 正常 | 正常 | 正常 | 正常收尾 | 「知识库暂不可用」，仍可查工单 |
| Redis 不可达 | 正常 | **拒绝写**（503，不写） | 退化为无记忆 | 退化为直查项目一 | 正常 | 对话仍可用；写操作提示稍后重试 |
| MySQL（审计）不可达 | 正常 | 正常 | 正常 | 正常 | 正常 | 无感；日志告警，审计缺失 |
| 项目一 + Redis 同时挂 | 工具不可见 | 不写 | 无记忆 | 匿名 | 正常 | 只能得到「服务暂不可用」类回答 |

> **注意**：项目一挂掉时，`PermService` 只能把「401 / 403 / 503 / 连接失败」统一当成「匿名」，所以用户可能看到「未登录或无权查询」，而不是「工单服务暂不可用」。这是 fail-closed 的代价，M5 明确接受；要区分得更细，需要给 `PermService` 增加「失败原因」枚举，属于后续优化。

### 3.5 fail-open / fail-closed 一览

| 能力 | 策略 | 理由 |
|---|---|---|
| 会话记忆 | **fail-open**（读不到当空、写失败只告警） | 记忆是体验，不是安全边界；不能因为 Redis 抖动让对话失败 |
| perms 缓存 | **fail-open**（缓存失败就绕过，直查项目一） | 缓存只是省调用；真正的权限仍由项目一裁决 |
| 写确认令牌 | **fail-closed**（存储不可用就拒绝写） | 令牌是「先预览」的工程护栏；没有它就不能保证两阶段，宁可不写 |
| 工具可见性 | **fail-closed**（拿不到 perms 就不下发工具） | M2 已确立的纪律 |
| RAG | **fail-open**（检索失败只影响该工具结果） | RAG 是增强，不是依赖 |
| 审计 | **fail-open**（写失败只告警） | 审计不能拖垮主流程 |
| 项目一写操作 | **fail-closed**（任何不确定都不写 / 不重试） | 写操作非幂等，M4 已有结论 |

## 四、Redis 接入基础（先打地基）

### 4.1 为什么用 `StringRedisTemplate` + JSON，而不是 `RedisTemplate<Object,Object>`

| 方案 | 问题 |
|---|---|
| `RedisTemplate<Object,Object>` + JDK 序列化 | Redis 里是二进制乱码，`redis-cli` 看不懂；类名 / `serialVersionUID` 变化会导致旧值反序列化失败；还有反序列化攻击面 |
| `RedisTemplate<String,Object>` + Jackson 泛型序列化 | 能看，但 `Object` 反序列化需要类型信息，配置复杂；不同 Spring AI 版本的对象结构变化容易踩坑 |
| **`StringRedisTemplate` + 自己定义的小 DTO + Jackson**（选它） | Redis 里是明文 JSON，可直接 `GET` 查看；结构变化可加版本号；只存自己的 DTO，不存 Spring AI 内部对象 |

M5 的 value 只有三类：`UserPerms`、`PendingWrite`、会话快照。它们都是**我们自己定义的 record**，用 Jackson 2 序列化没有歧义。

### 4.2 `JsonCodec`：把 JSON 异常收在一处

```java
package com.agentworkorder.redis;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.core.type.TypeReference;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.stereotype.Component;

import java.util.List;

/**
 * Redis value 的统一 JSON 编解码。
 *
 * <p>为什么单独抽一个类：三个 Redis 存储都要「序列化 / 反序列化 + 统一异常」，
 * 如果每个类各写一遍 try/catch，很容易漏掉某一处，最后变成「有的地方吞异常、有的地方抛 500」。
 *
 * <p>注意：这里用 Spring Boot 自动配置的 Jackson 2 ObjectMapper，
 * 不要自己 new 一个（会丢掉 Boot 注册的模块，比如 JavaTimeModule）。
 */
@Component
public class JsonCodec {

    private final ObjectMapper mapper;

    public JsonCodec(ObjectMapper mapper) {
        this.mapper = mapper;
    }

    public String toJson(Object value) {
        try {
            return mapper.writeValueAsString(value);
        } catch (JsonProcessingException e) {
            // 只存自己的简单 record，正常不会失败；失败说明代码有 bug，交给调用方决定降级方式
            throw new IllegalStateException("JSON 序列化失败", e);
        }
    }

    public <T> T fromJson(String json, Class<T> type) {
        try {
            return mapper.readValue(json, type);
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("JSON 反序列化失败", e);
        }
    }

    public <T> List<T> fromJsonList(String json, TypeReference<List<T>> type) {
        try {
            return mapper.readValue(json, type);
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("JSON 反序列化失败", e);
        }
    }
}
```

### 4.3 连接与超时：Redis 挂了不能等 10 秒

把 `application.yaml` 里的 Redis 超时改成：

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      password: ${REDIS_PASSWORD:change-me-redis}
      database: 5
      timeout: 2000            # 命令超时：从 10s 下调到 2s
      connect-timeout: 2000    # 建连超时（Lettuce 默认也偏长）
```

为什么必须改：

- M5 的降级逻辑是「Redis 命令失败 → 捕获 → 退化」。如果一条命令等 10 秒，会话记忆读 + 写、perms 读、令牌读各等 10 秒，用户会以为服务死了。
- 2 秒是经验值：正常 Redis 命令是亚毫秒级；2 秒还没回，基本可以判定不可用。

### 4.4 key 的命名、TTL 与内存策略

| 规则 | 做法 |
|---|---|
| 前缀 | 三个存储各自从配置读前缀，默认 `agent:chat:memory:` / `agent:perm:` / `agent:write:pending:` |
| TTL | **每个 key 都必须有**；会话 7 天、perms 60 秒、写令牌 300 秒 |
| 逻辑库 | 沿用 `database=5`，避开项目一的 `database=4` |
| 密码 | 继续走 `REDIS_PASSWORD` 环境变量；不要把生产密码写进 yaml |
| 淘汰策略 | 建议 `volatile-lru`（只淘汰带 TTL 的 key）；即使令牌被淘汰，写路径也是 fail-closed（用户重新预览即可），不会误写 |

### 4.5 本地起一个 Redis（验证用）

```bash
docker run -d --name agent-redis -p 6379:6379 \
  redis:7-alpine --requirepass change-me-redis

redis-cli -h localhost -p 6379 -a change-me-redis -n 5 ping
# PONG

# 看 M5 写了什么（开发环境用，生产不要 KEYS *）
redis-cli -h localhost -p 6379 -a change-me-redis -n 5 --scan --pattern "agent:*"
```

### 4.6 本节的常见坑

1. **`KEYS *` 会阻塞 Redis**：开发环境看看可以，代码里永远用 `SCAN`（§5.4 的 `findConversationIds` 就是 `SCAN`）。
2. **TTL 不是「过期删除」的保证**：Redis 过期是惰性 + 定期清理；读到过期 key 会当不存在，逻辑上没问题。
3. **`StringRedisTemplate` 默认 UTF-8**：中文消息没问题；不要再用 `new String(bytes)` 指定错编码。
4. **Redis 没起时应用通常能启动**：Lettuce 懒连接；但 Actuator 的 Redis health 会 DOWN，别把 Redis 放进「启动必须成功」的判断。

## 五、Redis 会话记忆

### 5.1 目标与不目标

| 目标 | 说明 |
|---|---|
| 重启不丢 | agent 重启后，同一 `sessionId` 还能接着聊 |
| 多实例共享 | 同一会话的下一轮请求落到另一台实例，也能读到历史 |
| 仍然只保留最近 N 条 | 沿用 `MessageWindowChatMemory` 的窗口，不让上下文无限膨胀 |
| 不改业务代码 | `SpringAiLlmClient` / `MessageChatMemoryAdvisor` 的用法不变 |

| 不目标 | 说明 |
|---|---|
| 会话列表 / 历史归档 | 记忆是「给模型的短期上下文」，不是业务档案；要归档应另建表 |
| 永久保存 | 默认 7 天 TTL；过期即丢，符合「会话」语义 |
| 保存工具调用的中间消息 | 只存 user / assistant / system 的文本，见 §5.3 |

### 5.2 关键设计：只换 Repository，不换 ChatMemory

```
MessageChatMemoryAdvisor
        │  add / get
        ▼
MessageWindowChatMemory（框架自带，负责「最近 20 条」）
        │  saveAll / findByConversationId
        ▼
ChatMemoryRepository（只有一个方法集）
        ├── InMemoryChatMemoryRepository（M1–M4）
        └── RedisChatMemoryRepository（M5，自己写）
```

这是 M5 最省事、也最不容易出错的地方：**窗口逻辑是框架的，持久化逻辑才是我们的**。不要把 `MessageWindowChatMemory` 一起重写。

### 5.3 存什么、不存什么

| 消息类型 | 存？ | 理由 |
|---|---|---|
| `UserMessage` | ✅ | 用户原话，多轮指代（「那第二张呢」）必须靠它 |
| `AssistantMessage`（有文本） | ✅ | 上一轮回答，模型需要接着上下文 |
| `AssistantMessage`（只有 tool call、文本为空） | ❌ | 空文本存了也没用；工具调用是「本轮脚手架」，不是对话内容 |
| `SystemMessage` | ✅（如果出现） | 系统提示一般由 `defaultSystem` 注入，不一定进记忆；出现就保留 |
| `ToolResponseMessage` | ❌ | 工具结果是**本轮**的中间产物；跨轮还原容易让模型看到「孤儿工具结果」，不同提供方兼容性也差 |

> 代价：跨轮看不到「上一轮工具返回的原始 JSON」。这是刻意的——上一轮的最终回答已经包含结论；真需要最新数据，这一轮重新调工具即可。**实时数据永远重新查，不靠记忆。**

### 5.4 `RedisChatMemoryRepository` 完整骨架

```java
package com.agentworkorder.memory;

import com.agentworkorder.redis.JsonCodec;
import lombok.extern.slf4j.Slf4j;
import org.springframework.ai.chat.memory.ChatMemoryRepository;
import org.springframework.ai.chat.messages.AssistantMessage;
import org.springframework.ai.chat.messages.Message;
import org.springframework.ai.chat.messages.MessageType;
import org.springframework.ai.chat.messages.SystemMessage;
import org.springframework.ai.chat.messages.UserMessage;
import org.springframework.data.redis.core.Cursor;
import org.springframework.data.redis.core.RedisCallback;
import org.springframework.data.redis.core.ScanOptions;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.util.StringUtils;

import java.nio.charset.StandardCharsets;
import java.time.Duration;
import java.util.ArrayList;
import java.util.List;

/**
 * Redis 版会话记忆仓库（M5）。
 *
 * <p>只实现 ChatMemoryRepository 的四个方法；「最近 N 条」仍由 MessageWindowChatMemory 负责。
 *
 * <p>值的结构（带版本号，方便将来改结构时兼容）：
 * <pre>
 * {
 *   "version": 1,
 *   "messages": [
 *     {"role": "user", "text": "..."},
 *     {"role": "assistant", "text": "..."}
 *   ]
 * }
 * </pre>
 *
 * <p>降级原则：<b>记忆是体验，不是安全边界</b>。任何 Redis / JSON 异常都只告警，
 * 读不到就当没有记忆，写失败也不影响本轮对话。
 */
@Slf4j
public class RedisChatMemoryRepository implements ChatMemoryRepository {

    /** 当前快照结构版本；结构不兼容时直接当空，避免把旧格式硬解析成错消息 */
    private static final int SNAPSHOT_VERSION = 1;

    private final StringRedisTemplate redis;
    private final JsonCodec codec;
    private final String keyPrefix;
    private final Duration ttl;

    public RedisChatMemoryRepository(StringRedisTemplate redis, JsonCodec codec,
                                     String keyPrefix, Duration ttl) {
        this.redis = redis;
        this.codec = codec;
        this.keyPrefix = keyPrefix;
        this.ttl = ttl;
    }

    /**
     * 管理 / 运维用：列出所有会话 id。
     * <p>用 SCAN 而不是 KEYS：KEYS 在大 key 空间会阻塞 Redis。
     */
    @Override
    public List<String> findConversationIds() {
        try {
            List<String> ids = redis.execute((RedisCallback<List<String>>) connection -> {
                List<String> result = new ArrayList<>();
                ScanOptions options = ScanOptions.scanOptions()
                        .match(keyPrefix + "*")
                        .count(200)
                        .build();
                try (Cursor<byte[]> cursor = connection.keyCommands().scan(options)) {
                    cursor.forEachRemaining(key -> {
                        String raw = new String(key, StandardCharsets.UTF_8);
                        result.add(raw.substring(keyPrefix.length()));
                    });
                }
                return result;
            });
            return ids == null ? List.of() : ids;
        } catch (Exception e) {
            log.warn("扫描会话记忆失败（不影响对话）：{}", e.toString());
            return List.of();
        }
    }

    @Override
    public List<Message> findByConversationId(String conversationId) {
        try {
            String json = redis.opsForValue().get(key(conversationId));
            if (!StringUtils.hasText(json)) {
                return List.of();
            }
            MemorySnapshot snapshot = codec.fromJson(json, MemorySnapshot.class);
            if (snapshot == null || snapshot.version() != SNAPSHOT_VERSION || snapshot.messages() == null) {
                return List.of();
            }
            List<Message> messages = new ArrayList<>(snapshot.messages().size());
            for (StoredMessage stored : snapshot.messages()) {
                Message message = toMessage(stored);
                if (message != null) {
                    messages.add(message);
                }
            }
            return messages;
        } catch (Exception e) {
            // Redis 挂了 / JSON 坏了：当没有记忆，不要让对话失败
            log.warn("读取会话记忆失败，按无记忆处理：conversation={} err={}",
                    conversationId, e.toString());
            return List.of();
        }
    }

    @Override
    public void saveAll(String conversationId, List<Message> messages) {
        try {
            List<StoredMessage> stored = new ArrayList<>();
            for (Message message : messages) {
                String role = roleOf(message.getMessageType());
                if (role == null) {
                    continue;   // TOOL 消息不落库
                }
                String text = message.getText();
                if (!StringUtils.hasText(text)) {
                    continue;   // 只有 tool call、没有文本的 assistant 消息不落库
                }
                stored.add(new StoredMessage(role, text));
            }
            MemorySnapshot snapshot = new MemorySnapshot(SNAPSHOT_VERSION, stored);
            redis.opsForValue().set(key(conversationId), codec.toJson(snapshot), ttl);
        } catch (Exception e) {
            log.warn("写入会话记忆失败，本轮对话继续（下次会少一段上下文）：conversation={} err={}",
                    conversationId, e.toString());
        }
    }

    @Override
    public void deleteByConversationId(String conversationId) {
        try {
            redis.delete(key(conversationId));
        } catch (Exception e) {
            log.warn("删除会话记忆失败：conversation={} err={}", conversationId, e.toString());
        }
    }

    private String key(String conversationId) {
        return keyPrefix + conversationId;
    }

    /** 只处理三种「对话文本」消息；TOOL 返回 null，调用方跳过。 */
    private static String roleOf(MessageType type) {
        return switch (type) {
            case USER -> "user";
            case ASSISTANT -> "assistant";
            case SYSTEM -> "system";
            case TOOL -> null;
        };
    }

    private static Message toMessage(StoredMessage stored) {
        if (stored == null || !StringUtils.hasText(stored.role()) || !StringUtils.hasText(stored.text())) {
            return null;
        }
        return switch (stored.role()) {
            case "user" -> new UserMessage(stored.text());
            case "assistant" -> new AssistantMessage(stored.text());
            case "system" -> new SystemMessage(stored.text());
            default -> null;
        };
    }

    /** 一条落库消息：只保留角色 + 文本，不碰 Spring AI 的内部字段。 */
    public record StoredMessage(String role, String text) {
    }

    /** 快照：版本 + 消息列表。 */
    public record MemorySnapshot(int version, List<StoredMessage> messages) {
    }
}
```

### 5.6 用户维度隔离：`conversationId` 不能只用 sessionId

`SpringAiLlmClient` 里改两处（其余不动）：

```java
@Override
public Flux<String> stream(String sessionId, String userMessage, String authToken, String traceId) {
    String effectiveTraceId = StringUtils.hasText(traceId) ? traceId : java.util.UUID.randomUUID().toString();

    UserPerms perms = permService.load(authToken, effectiveTraceId);

    // 关键：记忆键 = 用户 + 会话，防止 B 用户传 A 用户的 sessionId 读到 A 的历史
    String conversationId = (perms.userId() == null ? "anon" : perms.userId().toString())
            + ":" + sessionId;

    return chatClient.prompt()
            .user(userMessage)
            .advisors(spec -> spec.param(ChatMemory.CONVERSATION_ID, conversationId))
            .toolCallbacks(visibleToolCallbacks(perms))
            // 审计仍记录原始 sessionId；记忆用带用户前缀的 conversationId
            .toolContext(ToolContextKeys.build(authToken, sessionId, effectiveTraceId, perms, provider))
            .stream()
            .content();
}
```

> 为什么审计仍存原始 `sessionId`：审计要回答「哪轮会话」，原始 sessionId 是前端看到的那个；把 userId 前缀混进去反而不好查。记忆键和审计键**用途不同，不必强求一致**。

### 5.7 窗口、TTL、并发与隐私

| 维度 | 结论 |
|---|---|
| 窗口 | `MessageWindowChatMemory.maxMessages=20`，与 M1–M4 一致；窗口按**原始消息**计数，落库时再过滤掉 tool 消息 |
| TTL | 默认 7 天；每次 `saveAll` 刷新；用户长期不聊自然过期 |
| 并发 | 同一 `sessionId` 的两个并发请求可能「后写覆盖先写」；这与原内存版行为一致，M5 不引入分布式锁 |
| 隐私 | 只存 user / assistant 文本；不存 JWT、不存工具原始返回、不存用户密码 |
| 多实例 | 下一轮请求落到任意实例都能读到；SSE 连接本身不需要粘性会话 |

> 一个细节：如果一轮对话里工具消息很多，`MessageWindowChatMemory` 的 20 条窗口可能大部分被 tool 消息占掉，落库后的文本消息会少于 20 条。这是可接受的——记忆的目的不是「精确 20 条」，而是「给模型足够近的上下文」。

```bash
# 4) 换一个用户 token，传同一个 sessionId——不应读到上一个用户的记忆
```

### 5.9 本节的常见坑

1. **不要直接序列化 `Message`**。`Message` 是接口，实现类带 tool call、metadata、media 等字段；Jackson 很难在反序列化时还原具体子类，Spring AI 升级也可能改结构。只存 `role + text` 最稳。
2. **不要存 `ToolResponseMessage`**。跨轮还原会出现「只有工具结果、没有对应 tool call」的孤儿消息，部分提供方会直接报 400。
3. **`AssistantMessage.getText()` 可能为 null**（纯 tool call 消息）；落库前必须 `StringUtils.hasText` 过滤。
4. **`findConversationIds` 用 `SCAN`，不要 `KEYS`**；`SCAN` 的 `count` 只是提示，不是精确值。
5. **`saveAll` 的语义是「全量替换」**，不是追加；所以每次 `SET` 新 JSON 是对的，不要用 `RPUSH`。
6. **TTL 要在每次保存时刷新**；`SET key value EX` 正好满足。

## 六、SSE 协议、心跳与错误

### 6.1 现状与目标

现状：只有无名 `data:` 帧；没有心跳；错误直接断流。目标：定义一套**客户端可解析、可收尾**的协议，同时尽量不破坏旧的「只取 data」解析器。

### 6.2 协议 v2

| 帧 | SSE 字段 | data | 含义 | 客户端动作 |
|---|---|---|---|---|
| 文本增量 | 无名（默认 `message`） | 模型输出的一段文本 | 正常 token | 追加到气泡 |
| 正常结束 | `event: done` | `{"traceId":"...","durationMs":1234}` | 流正常结束 | 停止 loading；记录 traceId |
| 错误结束 | `event: error` | `{"code":503,"message":"...","retryable":true,"traceId":"..."}` | 流以错误结束 | 显示 message；`retryable` 决定是否给「重试」按钮 |
| 心跳 | 注释行 `:hb` | 无 | 连接还活着 | 忽略；用于重置网关空闲计时 |

时序：

```
客户端 GET /api/agent/chat
  │
  ├─ data: 工单从提交...
  ├─ data: 一般会经过...
  │      （模型思考中，15s 没输出）
  ├─ :hb
  ├─ :hb
  ├─ data: 待审核、待派单...
  ├─ event: done
  └─ （连接关闭）
```

错误时：

```
  ├─ data: 我先查一下...
  ├─ event: error
  └─ （连接关闭，不再发 done）
```

**规则：`done` 与 `error` 互斥，且都必须是最后一帧。** 客户端把任意一个都当作「流结束」。

### 6.3 控制器完整骨架

```java
package com.agentworkorder.controller;

import com.agentworkorder.config.SseProperties;
import com.agentworkorder.llm.LlmClient;
import com.agentworkorder.sse.AgentSseEvents;
import jakarta.servlet.http.HttpServletResponse;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.codec.ServerSentEvent;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import java.time.Duration;
import java.util.UUID;
import java.util.regex.Pattern;

/**
 * 对外唯一入口：SSE 流式对话（M5 协议 v2）。
 *
 * <p>M5 加了四件事：
 * <ol>
 *   <li>sessionId / message 入参校验（也顺手防了超长 Redis key）；</li>
 *   <li>统一 traceId，并通过响应头 X-Trace-Id 返回；</li>
 *   <li>空闲超时 → error 事件；正常结束 → done 事件；</li>
 *   <li>每 15 秒一个 SSE 注释心跳，防止网关掐连接。</li>
 * </ol>
 */
@Slf4j
@RestController
@RequestMapping("/api/agent")
public class AgentChatController {

    /** sessionId 只允许这些字符：既能做 Redis key，也不会造成 key 注入 */
    private static final Pattern SESSION_ID = Pattern.compile("[A-Za-z0-9_-]{1,64}");

    private final LlmClient llmClient;
    private final AgentSseEvents events;
    private final SseProperties properties;

    public AgentChatController(LlmClient llmClient, AgentSseEvents events, SseProperties properties) {
        this.llmClient = llmClient;
        this.events = events;
        this.properties = properties;
    }

    @GetMapping(value = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> chat(
            @RequestParam String sessionId,
            @RequestParam String message,
            @RequestHeader(value = HttpHeaders.AUTHORIZATION, required = false) String authorization,
            HttpServletResponse response) {

        // 步骤 1：同步校验。校验失败直接 400，不进入 SSE（客户端拿到普通 JSON 错误）
        if (!SESSION_ID.matcher(sessionId).matches()) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST,
                    "sessionId 只能包含字母、数字、下划线、连字符，长度 1-64");
        }
        if (message == null || message.isBlank()) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "message 不能为空");
        }
        if (message.length() > properties.getMaxMessageChars()) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST,
                    "message 不能超过 " + properties.getMaxMessageChars() + " 字");
        }

        // 步骤 2：一轮对话一个 traceId；响应头先给客户端，后面 done/error 里也有
        String traceId = UUID.randomUUID().toString();
        long start = System.currentTimeMillis();
        response.setHeader("X-Trace-Id", traceId);
        response.setHeader(HttpHeaders.CACHE_CONTROL, "no-cache");
        response.setHeader("X-Accel-Buffering", "no");   // Nginx 不缓冲

        // 步骤 3：Flux.defer 很关键——让 llmClient.stream 里的同步异常也变成流上的 error，
        //         从而被下面的 onErrorResume 捕获，而不是在 controller 返回前直接抛出。
        Flux<ServerSentEvent<String>> body = Flux.defer(() ->
                        llmClient.stream(sessionId, message, authorization, traceId))
                .map(events::token)
                .timeout(Duration.ofSeconds(Math.max(1, properties.getIdleTimeoutSeconds())))
                .concatWith(Mono.fromSupplier(() ->
                        events.done(traceId, System.currentTimeMillis() - start)))
                // 放在 concatWith 之后：正常路径会发 done；异常路径只发 error，不会再补 done
                .onErrorResume(e -> {
                    // 日志保留完整堆栈；发给客户端的只有脱敏后的 code/message
                    log.error("SSE 流异常：trace={}", traceId, e);
                    return Flux.just(events.error(traceId, e));
                });

        // 步骤 4：心跳与正文合并；takeUntil 保证看到 done/error 就取消心跳并正常结束
        Flux<ServerSentEvent<String>> heartbeat = Flux
                .interval(Duration.ofSeconds(Math.max(1, properties.getHeartbeatSeconds())))
                .map(i -> events.heartbeat());

        return Flux.merge(body, heartbeat)
                .takeUntil(events::isTerminal)
                .doOnCancel(() -> log.info("客户端断开：trace={}", traceId));
    }

    /**
     * 连通性自测（调试用）：走同一个 LlmClient，阻塞收集全部 token。
     * <p>M5 只补了 traceId 与 60 秒上限；它不是产品接口。
     */
    @GetMapping("/hello")
    public String hello(@RequestParam String context) {
        String traceId = UUID.randomUUID().toString();
        return llmClient.stream("hello-test", context, null, traceId)
                .collectList()
                .map(tokens -> String.join("", tokens))
                .block(Duration.ofSeconds(60));
    }
}
```

### 6.4 事件工厂与错误映射

```java
package com.agentworkorder.sse;

import com.agentworkorder.metrics.AgentMetrics;
import com.agentworkorder.resilience.CircuitOpenException;
import com.fasterxml.jackson.databind.ObjectMapper;
import lombok.extern.slf4j.Slf4j;
import org.springframework.ai.retry.NonTransientAiException;
import org.springframework.ai.retry.TransientAiException;
import org.springframework.http.codec.ServerSentEvent;
import org.springframework.stereotype.Component;
import org.springframework.web.client.RestClientException;
import org.springframework.web.reactive.function.client.WebClientException;

import java.util.LinkedHashMap;
import java.util.Map;
import java.util.concurrent.TimeoutException;

/**
 * SSE 事件工厂：把「协议细节」收在一个类里，controller 只负责编排。
 *
 * <p>为什么错误映射要单独写：异常类型很多（超时、熔断、模型 4xx、网关 5xx），
 * 但客户端只需要「一个可读消息 + 一个是否可重试的布尔值」。不要把堆栈直接丢给前端。
 */
@Slf4j
@Component
public class AgentSseEvents {

    private final ObjectMapper mapper;
    private final AgentMetrics metrics;

    public AgentSseEvents(ObjectMapper mapper, AgentMetrics metrics) {
        this.mapper = mapper;
        this.metrics = metrics;
    }

    /** 文本增量：刻意不加 event 名，保持旧客户端「只取 data」也能工作 */
    public ServerSentEvent<String> token(String token) {
        return ServerSentEvent.<String>builder(token).build();
    }

    /** 正常结束：仅此一帧，之后流关闭 */
    public ServerSentEvent<String> done(String traceId, long durationMs) {
        Map<String, Object> data = new LinkedHashMap<>();
        data.put("traceId", traceId);
        data.put("durationMs", durationMs);
        return ServerSentEvent.<String>builder(toJson(data))
                .event("done")
                .build();
    }

    /** 错误结束：仅此一帧；客户端看到 event=error 就停止 loading */
    public ServerSentEvent<String> error(String traceId, Throwable throwable) {
        ErrorInfo info = map(throwable);
        metrics.sseError(info.code());

        Map<String, Object> data = new LinkedHashMap<>();
        data.put("code", info.code());
        data.put("message", info.message());
        data.put("retryable", info.retryable());
        data.put("traceId", traceId);

        return ServerSentEvent.<String>builder(toJson(data))
                .event("error")
                .build();
    }

    /** 心跳：SSE 注释行，客户端不会触发 onmessage，只用来保活 */
    public ServerSentEvent<String> heartbeat() {
        return ServerSentEvent.<String>builder().comment("hb").build();
    }

    public boolean isTerminal(ServerSentEvent<String> event) {
        return "done".equals(event.event()) || "error".equals(event.event());
    }

    private ErrorInfo map(Throwable throwable) {
        if (throwable instanceof CircuitOpenException) {
            return new ErrorInfo(503, "服务暂时繁忙，请稍后重试", true);
        }
        if (throwable instanceof TimeoutException) {
            return new ErrorInfo(504, "模型响应超时，请稍后重试", true);
        }
        if (throwable instanceof NonTransientAiException) {
            // 4xx：key / model / base-url 配错，重试也没用
            return new ErrorInfo(502, "模型服务配置异常，请联系管理员", false);
        }
        if (throwable instanceof TransientAiException
                || throwable instanceof RestClientException
                || throwable instanceof WebClientException) {
            return new ErrorInfo(502, "模型服务暂时不可用，请稍后重试", true);
        }
        return new ErrorInfo(500, "服务内部错误，请稍后重试", true);
    }

    private String toJson(Map<String, Object> data) {
        try {
            return mapper.writeValueAsString(data);
        } catch (Exception e) {
            // 只含基本类型，正常不会失败；兜底一个合法 JSON
            return "{\"code\":500,\"message\":\"事件序列化失败\"}";
        }
    }

    /** 错误映射结果：给客户端的最小信息 */
    private record ErrorInfo(int code, String message, boolean retryable) {
    }
}
```

常见异常到事件的映射：

| 异常 | 事件 code | 文案 | `retryable` |
|---|---|---|---|
| `CircuitOpenException` | 503 | 服务暂时繁忙，请稍后重试 | true |
| `TimeoutException` | 504 | 模型响应超时，请稍后重试 | true |
| `NonTransientAiException` | 502 | 模型服务配置异常，请联系管理员 | false |
| `TransientAiException` / `RestClientException` / `WebClientException` | 502 | 模型服务暂时不可用，请稍后重试 | true |
| 其他 | 500 | 服务内部错误，请稍后重试 | true |

### 6.5 客户端解析（fetch + ReadableStream）

浏览器原生 `EventSource` **不能设置 `Authorization` 头**，所以继续用 `fetch` 读流。前端需要把「无名 token 帧」和「命名控制帧」分开：

```ts
export type ChatHandlers = {
  onDelta: (text: string) => void;
  onDone?: (meta: { traceId: string; durationMs: number }) => void;
  onError?: (err: { code: number; message: string; retryable: boolean; traceId: string }) => void;
};

export async function streamChat(
  baseUrl: string,
  token: string,
  sessionId: string,
  message: string,
  handlers: ChatHandlers,
  signal?: AbortSignal,
): Promise<void> {
  const url = `${baseUrl}/api/agent/chat?sessionId=${encodeURIComponent(sessionId)}`
            + `&message=${encodeURIComponent(message)}`;

  const res = await fetch(url, {
    headers: {
      Authorization: token.startsWith('Bearer ') ? token : `Bearer ${token}`,
      Accept: 'text/event-stream',
    },
    signal,
  });
  if (!res.ok || !res.body) {
    throw new Error(`Agent 请求失败：HTTP ${res.status}`);
  }

  const reader = res.body.getReader();
  const decoder = new TextDecoder('utf-8');
  let buffer = '';

  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });

    // SSE 帧以空行分隔
    let match: RegExpExecArray | null;
    while ((match = /\r?\n\r?\n/.exec(buffer)) !== null) {
      const frame = buffer.slice(0, match.index);
      buffer = buffer.slice(match.index + match[0].length);

      let eventName = 'message';
      const dataLines: string[] = [];
      for (const line of frame.split(/\r?\n/)) {
        if (line.startsWith(':')) continue;                 // 心跳注释
        if (line.startsWith('event:')) eventName = line.slice(6).trim();
        else if (line.startsWith('data:')) dataLines.push(line.slice(5).replace(/^ /, ''));
      }
      const data = dataLines.join('\n');
      if (!data) continue;

      if (eventName === 'done') {
        handlers.onDone?.(JSON.parse(data));
      } else if (eventName === 'error') {
        handlers.onError?.(JSON.parse(data));
      } else {
        // 无 event 名 = 文本增量
        handlers.onDelta(data);
      }
    }
  }
}
```

### 6.6 超时、断连与取消

| 场景 | 行为 |
|---|---|
| 模型 60 秒没有任何输出 | Reactor `timeout` → `event:error`（504），连接正常收尾 |
| 模型输出到一半报错 | 已输出内容保留；`event:error`；客户端不要清空气泡 |
| 用户点「停止」 | 客户端 `AbortController.abort()`；服务端 `doOnCancel` 记日志，上游取消 |
| 网关 60 秒空闲超时 | 心跳每 15 秒续命；网关 `proxy_read_timeout` 仍要调大 |
| 客户端断开 | 服务端取消订阅；不要在断开后继续调工具（Reactor 会取消） |

> **`timeout` 只能中断 Reactor 的等待，不能强行中断一个正在阻塞的工具调用。** 工具里的 `RestClient` 有自己的 2s / 10s 超时；Milvus 的 gRPC 超时要靠 Milvus SDK 配置。Reactor 的 `timeout` 是最后一道「至少让客户端收到错误」的保险。

### 6.8 兼容性与灰度

- **token 帧保持无名**：旧的「只取 data」解析器仍能正常追加文本。
- **`done` / `error` 是新增命名事件**：旧解析器如果只取 `data`，会把 `{"traceId":...}` 追加到回答末尾——所以**前后端要一起上线**。如果暂时不能改前端，可以先只发心跳、不发 done/error，等前端升级后再打开（加一个 `agent.sse.control-events-enabled` 开关）。
- **`X-Trace-Id` 响应头**：客户端日志、客服排查都能用；不含敏感信息。

### 6.9 本节的常见坑

1. **`Flux.merge` 里的心跳是无限流**：必须用 `takeUntil(done/error)` 取消，否则正文结束后连接永远不关闭。
2. **`onErrorResume` 要放在 `concatWith(done)` 之后**：这样正常路径有 done，异常路径只有 error；放前面会出现「error 后面又补一个 done」。
3. **`Flux.defer` 不能省**：`llmClient.stream(...)` 里如果有同步代码（取 perms、拼 prompt），不加 defer 时异常会在 controller 返回前抛出，SSE 头还没发，客户端拿到的是普通 500。
4. **不要在 `error` 之后继续 `data`**：SSE 客户端可能已经停止渲染；协议规定 error 是最后一帧。
5. **心跳不要用 `data:`**：那会触发客户端的 `onmessage`，被当成回答内容；用 `:` 注释行。
6. **`ServerSentEvent` 的 data 不要带换行**：JSON 里如果有换行，SSE 会拆成多行 `data:`；Jackson 默认不美化输出，没问题；不要手动 `prettyPrint`。
7. **`sessionId` 正则校验可能挡住旧前端**：如果历史前端传了中文 / 空格 / 点号，M5 会直接 400。上线前先确认前端用的是 UUID 或 `[A-Za-z0-9_-]`；否则把正则放宽到「只排除空白和控制字符」，但不要放弃长度上限。

## 七、降级与熔断

### 7.1 哪些依赖会挂，挂了会怎样

| 依赖 | 典型故障 | 不熔断的后果 | M5 的处理 |
|---|---|---|---|
| 项目一 | 进程挂了 / 网络不通 / 数据库锁 | 每次工具调用等 10s 超时；模型上下文被拖死 | 熔断 `project-one`，5 次失败后 30s 内快速失败 |
| LLM | key 失效 / 限流 / 网络抖动 | 每次对话等首 token；用户以为页面卡死 | 熔断 `llm`，直接发 `event:error` |
| RAG（Milvus / embedding） | 容器没起 / 模型 404 | 每次检索等一次失败；拖慢整轮 | 熔断 `rag`，检索工具返回 503 错误体 |
| MySQL（审计） | 连接池满 / 表锁 | 审计插入阻塞工具调用 | 不熔断；语句超时 + 吞异常 |
| Redis | 挂了 / 网络分区 | 记忆、perms、令牌都失败 | 按 §3.5 分别 fail-open / fail-closed |

### 7.2 选型：自研 vs Sentinel vs Resilience4j

| 方案 | 优点 | 代价 | M5 结论 |
|---|---|---|---|
| **Sentinel** | 生产级、控制台、集群流控、热点参数、系统自适应 | 多一套依赖与版本对齐；控制台 / 传输模块另起；对 `RestClient` 这种任意调用仍要手写 `SphU.entry`；概念多，不适合「手写一遍就懂」 | 不作为默认；附录 B 给等价接法 |
| **Resilience4j** | 轻量、Spring Boot 集成好、注解 + 函数式都支持 | 仍是一个新依赖；注解走 AOP，内部调用会失效；对「按资源名 + 两套 fallback」的定制不如自己写直观 | 不选 |
| **自研 100 行熔断器**（选它） | 逻辑全透明、可单测、无新依赖；能精确区分「熔断拒绝」与「调用失败」两种 fallback；面试时能讲清每个字段 | 没有控制台、没有集群规则、没有滑动窗口 | **M5 默认** |

> 这不是说 Sentinel 不好，而是说 **M5 的需求只有「下游挂了别一直打」**。Sentinel 的价值在「流控平台」，本项目当前没有多租户、没有大促、没有集群规则；用一个 100 行的状态机把「熔断」这件事讲透，比引一整套平台更适合这个阶段。
>
> 如果答辩 / 简历要求必须出现 Sentinel，附录 B 给出 `SphU.entry` 的等价写法；业务代码只依赖 `ResilienceGuard`，换实现不影响工具与 controller。

### 7.3 状态机与参数

```
                失败次数 >= 阈值
   CLOSED ──────────────────────▶ OPEN
     ▲                              │
     │ 试探成功                      │ 等待 open-seconds
     │                              ▼
     └──────── HALF_OPEN ◀──────────┘
                  │
                  └── 试探失败 ──▶ OPEN（重新计时）
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `failure-threshold` | 5 | **连续**失败多少次后打开；不是滑动窗口，实现简单、行为可预测 |
| `open-seconds` | 30 | 打开后多久允许一次试探 |
| `half-open-max-calls` | 1 | 半开状态最多放几个试探请求；默认 1，避免恢复瞬间又被压垮 |
| 计数粒度 | 每个资源名一个熔断器 | `project-one` / `llm` / `rag` 互不影响 |

> 为什么用「连续失败」而不是「滑动窗口失败率」：滑动窗口更精确，但要维护时间桶、并发统计和边界条件，代码量翻倍；对本项目「下游整体挂掉」这种场景，连续失败已经足够。将来要更精确，只需替换 `CircuitBreaker` 内部实现，`ResilienceGuard` 接口不变。
>
> **一个刻意接受的取舍**：读接口和写接口共用 `project-one` 这一个熔断器。如果只是写接口单独出问题，读接口也会被一起快速失败。这是保守策略——「同一个下游已经明显不健康，先别再打它」；如果将来要拆细，可以把资源名改成 `project-one-read` / `project-one-write`，`ResilienceGuard` 不用改。

### 7.4 `CircuitBreaker` 完整骨架

```java
package com.agentworkorder.resilience;

import lombok.extern.slf4j.Slf4j;

import java.util.concurrent.TimeUnit;

/**
 * 一个很小的熔断器：CLOSED / OPEN / HALF_OPEN 三态。
 *
 * <p>为什么方法都加 synchronized：熔断判断是「读 + 改状态」的复合操作，
 * 用 Atomic 系列要写 CAS 循环，反而不如一把锁直观；这里的调用频率是「每次下游调用一次」，
 * 临界区只有几个赋值，锁竞争可以忽略。
 *
 * <p>为什么失败计数在 trip 后清零：OPEN 期间不再累计；半开失败会直接重新 trip。
 */
@Slf4j
public class CircuitBreaker {

    public enum State {
        CLOSED, OPEN, HALF_OPEN
    }

    private final String name;
    private final int failureThreshold;
    private final long openNanos;
    private final int halfOpenMaxCalls;

    private State state = State.CLOSED;
    private int consecutiveFailures = 0;
    private long openUntilNanos = 0L;
    private int halfOpenCalls = 0;

    public CircuitBreaker(String name, int failureThreshold, int openSeconds, int halfOpenMaxCalls) {
        this.name = name;
        this.failureThreshold = Math.max(1, failureThreshold);
        this.openNanos = TimeUnit.SECONDS.toNanos(Math.max(1, openSeconds));
        this.halfOpenMaxCalls = Math.max(1, halfOpenMaxCalls);
    }

    /**
     * 尝试放行一次调用。
     *
     * @return true=可以调用；false=熔断中，调用方应直接走 fallback
     */
    public synchronized boolean tryAcquire() {
        switch (state) {
            case CLOSED:
                return true;
            case OPEN:
                if (System.nanoTime() >= openUntilNanos) {
                    state = State.HALF_OPEN;
                    halfOpenCalls = 1;
                    log.info("熔断器 {} 进入半开（HALF_OPEN），放行 1 次试探", name);
                    return true;
                }
                return false;
            case HALF_OPEN:
                if (halfOpenCalls < halfOpenMaxCalls) {
                    halfOpenCalls++;
                    return true;
                }
                return false;
            default:
                return false;
        }
    }

    /** 调用成功：无论之前什么状态，都恢复 CLOSED */
    public synchronized void recordSuccess() {
        if (state != State.CLOSED) {
            log.info("熔断器 {} 试探成功，恢复 CLOSED", name);
        }
        state = State.CLOSED;
        consecutiveFailures = 0;
        halfOpenCalls = 0;
    }

    /** 调用失败：CLOSED 下累计；HALF_OPEN 下直接重新打开 */
    public synchronized void recordFailure() {
        if (state == State.HALF_OPEN) {
            trip();
            return;
        }
        consecutiveFailures++;
        if (consecutiveFailures >= failureThreshold) {
            trip();
        }
    }

    private void trip() {
        state = State.OPEN;
        openUntilNanos = System.nanoTime() + openNanos;
        halfOpenCalls = 0;
        consecutiveFailures = 0;
        log.warn("熔断器 {} 打开（OPEN），{} 秒后允许试探",
                name, TimeUnit.NANOSECONDS.toSeconds(openNanos));
    }

    public synchronized State state() {
        return state;
    }

    public synchronized boolean isOpen() {
        return state == State.OPEN;
    }

    public synchronized int consecutiveFailures() {
        return consecutiveFailures;
    }
}
```

### 7.5 `ResilienceGuard`：按资源名取熔断器 + 两种 fallback

```java
package com.agentworkorder.resilience;

import com.agentworkorder.config.ResilienceProperties;
import com.agentworkorder.metrics.AgentMetrics;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;
import reactor.core.publisher.Flux;

import java.util.LinkedHashMap;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Function;
import java.util.function.Supplier;

/**
 * 熔断 + fallback 的统一入口。
 *
 * <p>为什么区分 whenOpen / whenFailed：
 * <ul>
 *   <li><b>whenOpen</b>：熔断器直接拒绝，请求<b>一定没有发出去</b>，写操作可以告诉用户「未提交」；</li>
 *   <li><b>whenFailed</b>：请求发出后异常（超时 / 连接断），写操作<b>可能已经执行</b>，
 *       只能告诉用户「结果未知，请先查询」。</li>
 * </ul>
 * 这个区别对读操作无所谓，对写操作非常关键（M4 §7.4）。
 */
@Slf4j
@Component
public class ResilienceGuard {

    private static final String RESOURCE_PROJECT_ONE = "project-one";
    private static final String RESOURCE_LLM = "llm";
    private static final String RESOURCE_RAG = "rag";

    private final ResilienceProperties properties;
    private final AgentMetrics metrics;
    private final Map<String, CircuitBreaker> breakers = new ConcurrentHashMap<>();

    public ResilienceGuard(ResilienceProperties properties, AgentMetrics metrics) {
        this.properties = properties;
        this.metrics = metrics;
    }

    /**
     * 包裹一次同步调用。
     *
     * @param resource   资源名（project-one / llm / rag）
     * @param action     真正调用
     * @param whenOpen   熔断拒绝时的返回值
     * @param whenFailed 调用抛异常时的返回值
     */
    public <T> T call(String resource, Supplier<T> action,
                      Supplier<T> whenOpen, Function<RuntimeException, T> whenFailed) {
        if (!properties.isEnabled()) {
            try {
                return action.get();
            } catch (RuntimeException e) {
                return whenFailed.apply(e);
            }
        }

        CircuitBreaker breaker = breaker(resource);
        if (!breaker.tryAcquire()) {
            metrics.circuitRejected(resource);
            log.warn("熔断中，快速失败：resource={}", resource);
            return whenOpen.get();
        }

        try {
            T result = action.get();
            breaker.recordSuccess();
            return result;
        } catch (RuntimeException e) {
            breaker.recordFailure();
            metrics.circuitFailure(resource);
            log.warn("下游调用失败：resource={} err={}", resource, e.toString());
            return whenFailed.apply(e);
        }
    }

    /**
     * 包裹一条响应式流（LLM 用）。
     * <p>成功判定是「流正常结束」；中途报错算失败；客户端主动取消不算失败。
     */
    public <T> Flux<T> guardFlux(String resource, Flux<T> upstream) {
        if (!properties.isEnabled()) {
            return upstream;
        }
        CircuitBreaker breaker = breaker(resource);
        return Flux.defer(() -> {
            if (!breaker.tryAcquire()) {
                metrics.circuitRejected(resource);
                return Flux.error(new CircuitOpenException(resource));
            }
            return upstream
                    .doOnComplete(breaker::recordSuccess)
                    .doOnError(e -> {
                        breaker.recordFailure();
                        metrics.circuitFailure(resource);
                    });
        });
    }

    /** 健康检查 / 指标用：资源名 → 当前状态 */
    public Map<String, String> states() {
        Map<String, String> result = new LinkedHashMap<>();
        breakers.forEach((name, breaker) -> result.put(name, breaker.state().name()));
        return result;
    }

    private CircuitBreaker breaker(String resource) {
        return breakers.computeIfAbsent(resource, name -> {
            CircuitBreaker created = new CircuitBreaker(
                    name,
                    properties.getFailureThreshold(),
                    properties.getOpenSeconds(),
                    properties.getHalfOpenMaxCalls());
            metrics.registerCircuitBreaker(name, created);
            return created;
        });
    }
}
```

### 7.10 读 / 写 fallback 文案对照

| 场景 | 读工具返回 | 写工具返回 | 模型应怎么说 |
|---|---|---|---|
| 熔断器打开 | `{"code":503,"message":"工单服务暂不可用，请稍后重试"}` | `{"code":503,"message":"写操作未提交：工单服务暂不可用，请稍后重新预览"}` | 「服务暂不可用，本次没有修改」 |
| 调用超时 | 同上 | `{"code":500,"message":"写操作结果未知，请先查询工单当前状态再决定是否重试"}` | 「结果不确定，我先帮你查当前状态」 |
| 项目一业务错误 | 项目一原始 `{code,message}` | 项目一原始 `{code,message}` | 如实转述 code/message |
| Redis 令牌不可用 | — | `{"code":503,"message":"写操作暂不可用，请稍后重试"}` | 「确认服务暂不可用，未修改」 |

### 7.11 为什么不做自动重试

| 类型 | 重试？ | 原因 |
|---|---|---|
| 读工具 | 不自动重试 | 重试会放大下游压力；熔断器已经负责「别再打」；用户/模型可以再发一次 |
| 写工具 | **绝不自动重试** | 非幂等；超时可能已写成功；M4 §7.4 已确立 |
| LLM 流 | 不自动重试 | 已输出一半的内容无法回滚；重试会产生重复回答；让客户端决定 |
| Redis 命令 | 不自动重试 | Lettuce 自己有重连；我们的策略是快速降级 |

### 7.12 本节的常见坑

1. **`call` 只应包住「传输层」**。不要把它包在业务判断外面，否则 `WriteRejectedException(409)` 会被当成下游失败，甚至触发熔断。
2. **半开只放 1 个请求**。如果放太多，恢复瞬间可能又把下游打挂。
3. **熔断器是每实例独立的**。A 实例打开，B 实例可能还是关闭；这不是 bug，是「每实例自保」。要做集群级熔断，才需要 Sentinel 集群规则。
4. **流式调用的「成功」定义是正常结束**。如果模型输出到一半断了，记失败是合理的。
5. **熔断打开时的 fallback 不要伪装成空数据**。空列表会让模型说「你没有工单」，这是错误事实；必须返回 `503`。
6. **`whenOpen` 与 `whenFailed` 不能混用**。写操作混用会把「没提交」说成「结果未知」，或者反过来，都是误导。

```java
package com.agentworkorder.perm;

import java.time.Duration;

/**
 * 用户权限缓存的端口（M5）。
 *
 * <p>缓存只是「省一次项目一调用」，不是权限事实来源；实现可以失败，

public interface PermCache {

    UserPerms get(String tokenHash);
```

**进程内实现（回滚 / 无 Redis 开发用）**

```java
package com.agentworkorder.perm;

import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.concurrent.ConcurrentHashMap;

@Component
@ConditionalOnProperty(name = "agent.perm.cache-store", havingValue = "memory", matchIfMissing = true)
public class MemoryPermCache implements PermCache {

    private final ConcurrentHashMap<String, Cached> cache = new ConcurrentHashMap<>();

    @Override
    public UserPerms get(String tokenHash) {
        Cached cached = cache.get(tokenHash);
        if (cached == null) {
            return null;
        }
        if (cached.expiresAtMillis() <= System.currentTimeMillis()) {
            cache.remove(tokenHash);
            return null;
        }
        return cached.perms();
    }

    @Override
    public void put(String tokenHash, UserPerms perms, Duration ttl) {
        cache.put(tokenHash, new Cached(perms, System.currentTimeMillis() + ttl.toMillis()));
    }

    private record Cached(UserPerms perms, long expiresAtMillis) {
    }
}
```

**Redis 实现（默认）**

```java
package com.agentworkorder.perm;

import com.agentworkorder.config.PermProperties;
import com.agentworkorder.redis.JsonCodec;
import lombok.extern.slf4j.Slf4j;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.time.Duration;

@Slf4j
@Component
@ConditionalOnProperty(name = "agent.perm.cache-store", havingValue = "redis")
public class RedisPermCache implements PermCache {

    private final StringRedisTemplate redis;
    private final JsonCodec codec;
    private final String keyPrefix;

    public RedisPermCache(StringRedisTemplate redis, JsonCodec codec, PermProperties properties) {
        this.redis = redis;
        this.codec = codec;
        this.keyPrefix = properties.getKeyPrefix();
    }

    @Override
    public UserPerms get(String tokenHash) {
        try {
            String json = redis.opsForValue().get(keyPrefix + tokenHash);
            return json == null ? null : codec.fromJson(json, UserPerms.class);
        } catch (Exception e) {
            // 缓存故障 = miss，让 PermService 回源；不能因为缓存挂了就放行权限
            log.warn("读取 perms 缓存失败，回源项目一：{}", e.toString());
            return null;
        }
    }

    @Override
    public void put(String tokenHash, UserPerms perms, Duration ttl) {
        try {
            redis.opsForValue().set(keyPrefix + tokenHash, codec.toJson(perms), ttl);
        } catch (Exception e) {
            log.warn("写入 perms 缓存失败（不影响本轮）：{}", e.toString());
        }
    }
}
```

### 8.2 `PermService` 改造：只替换缓存那一层

```java

     */
    public UserPerms loadFresh(String authToken, String traceId) {
        if (!StringUtils.hasText(authToken)) {
            return UserPerms.ANONYMOUS;
        }
        return fetch(authToken, traceId);
    }

    // fetch / parse / sha256 保持 M2 的实现不变
}
```

> **为什么写确认前要 fresh**：perms 缓存 60 秒，管理员刚回收权限，用户在这 60 秒内仍然「看得见」写工具。项目一最终会 403，但 agent 侧多一道「确认时重查」更稳，也符合 M4 R38 的遗留项。
>
> **注意**：项目一不可达时 `loadFresh` 也返回 `ANONYMOUS`，所以写工具会拒绝并提示「权限校验未通过（可能已被收回或权限服务暂不可用）」。这是 fail-closed 的代价，不是 bug。

写工具里怎么用（放在 `confirm` 的最前面，**先查权限、再消费令牌**）：

```java
private String confirm(String toolName, String action, Long id, Boolean approved,
                       Long handlerId, String remark, String confirmationToken,
                       ToolContext toolContext) throws Exception {
    if (id == null || id <= 0) {
        throw new WriteRejectedException(400, "工单 ID 非法");
    }

    // 步骤 1：跳过缓存重查权限。失败就不消费令牌，用户还能拿同一个令牌重试
    UserPerms fresh = permService.loadFresh(tokenOf(toolContext), traceIdOf(toolContext));
    if (!permissionRegistry.visibleTo(toolName, fresh)) {
        throw new WriteRejectedException(403,
                "权限校验未通过（可能已被收回或权限服务暂不可用），写操作未执行");
    }

    // 步骤 2：消费令牌（一次性）→ 每轮限流 → 请求项目一
    PendingWrite pending = confirmationService.consume(
            confirmationToken, sessionIdOf(toolContext), userIdOf(toolContext), action, id,
            paramsOf(handlerId, approved, remark));
    writeGuard.checkAndCount(traceIdOf(toolContext));
    ToolChangeStatusRequest request = new ToolChangeStatusRequest(
            action, pending.observedFromStatus(), handlerId, approved, normalizeRemark(remark));
    return toolClient.changeStatus(id, request, tokenOf(toolContext));
}
```

> 注意：`handle(...)` 需要把 `toolName` 一起传给 `confirm(...)`；M4 的 `confirm` 没有这个参数，M5 要补上。

### 8.3 写确认令牌：抽出 `PendingWriteStore`

```java
package com.agentworkorder.write;

import java.time.Duration;

/**
 * 写确认令牌的存储端口（M5）。
 *
 * <p>语义要求：
 * <ul>
 *   <li>save：带 TTL 写入；</li>
 *   <li>consume：<b>原子地</b>取出并删除（一个令牌只能用一次）；</li>
 *   <li>isFull：仅进程内实现需要（Redis 靠 TTL 自然收敛）。</li>
 * </ul>
 */
public interface PendingWriteStore {

    void save(PendingWrite pending, Duration ttl);

    /** 原子取出并删除；不存在返回 null */
    PendingWrite consume(String token);

    default boolean isFull(int maxEntries) {
        return false;
    }
}
```

**进程内实现**

```java
package com.agentworkorder.write;

import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.concurrent.ConcurrentHashMap;

@Component
@ConditionalOnProperty(name = "agent.write.token-store", havingValue = "memory", matchIfMissing = true)
public class MemoryPendingWriteStore implements PendingWriteStore {

    private final ConcurrentHashMap<String, PendingWrite> pending = new ConcurrentHashMap<>();

    @Override
    public void save(PendingWrite write, Duration ttl) {
        long now = System.currentTimeMillis();
        pending.entrySet().removeIf(e -> e.getValue().expiresAtMillis() <= now);
        pending.put(write.token(), write);
    }

    @Override
    public PendingWrite consume(String token) {
        return pending.remove(token);
    }

    @Override
    public boolean isFull(int maxEntries) {
        // 先清过期项，避免「表里全是过期令牌却拒绝新预览」
        long now = System.currentTimeMillis();
        pending.entrySet().removeIf(e -> e.getValue().expiresAtMillis() <= now);
        return pending.size() >= maxEntries;
    }
}
```

**Redis 实现**

```java
package com.agentworkorder.write;

import com.agentworkorder.config.WriteProperties;
import com.agentworkorder.redis.JsonCodec;
import lombok.extern.slf4j.Slf4j;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.time.Duration;

@Slf4j
@Component
@ConditionalOnProperty(name = "agent.write.token-store", havingValue = "redis")
public class RedisPendingWriteStore implements PendingWriteStore {

    private final StringRedisTemplate redis;
    private final JsonCodec codec;
    private final String keyPrefix;

    public RedisPendingWriteStore(StringRedisTemplate redis, JsonCodec codec, WriteProperties properties) {
        this.redis = redis;
        this.codec = codec;
        this.keyPrefix = properties.getTokenKeyPrefix();
    }

    @Override
    public void save(PendingWrite write, Duration ttl) {
        try {
            redis.opsForValue().set(key(write.token()), codec.toJson(write), ttl);
        } catch (Exception e) {
            // 写路径 fail-closed：无法保存令牌就不允许进入「等待确认」
            log.warn("保存写确认令牌失败：{}", e.toString());
            throw new WriteRejectedException(503, "写操作暂不可用，请稍后重试");
        }
    }

    @Override
    public PendingWrite consume(String token) {
        try {
            // GETDEL：原子「取出并删除」，Redis 6.2+；天然防重放
            String json = redis.opsForValue().getAndDelete(key(token));
            return json == null ? null : codec.fromJson(json, PendingWrite.class);
        } catch (Exception e) {
            log.warn("消费写确认令牌失败：{}", e.toString());
            throw new WriteRejectedException(503, "写操作暂不可用，请稍后重试");
        }
    }

    private String key(String token) {
        return keyPrefix + token;
    }
}
```

### 8.4 `WriteConfirmationService` 改造

只改「存哪里」，令牌生成、指纹、绑定校验全部保留：

```java
@Service
public class WriteConfirmationService {

    private final WriteProperties properties;
    private final ObjectMapper objectMapper;
    private final PendingWriteStore store;          // ← M5：替换原来的 ConcurrentHashMap
    private final SecureRandom secureRandom = new SecureRandom();

    public WriteConfirmationService(WriteProperties properties, ObjectMapper objectMapper,
                                    PendingWriteStore store) {
        this.properties = properties;
        this.objectMapper = objectMapper;
        this.store = store;
    }

    public String issue(String sessionId, Long userId, Long orderId, String action,
                        Integer observedFromStatus, Map<String, Object> params) {
        if (store.isFull(properties.getMaxPreviewEntries())) {
            throw new WriteRejectedException(409, "待确认的预览过多，请稍后重试");
        }

        long now = System.currentTimeMillis();
        int ttlSeconds = Math.max(1, properties.getConfirmTtlSeconds());
        PendingWrite pending = new PendingWrite(
                randomToken(), sessionId, userId, orderId, action, observedFromStatus,
                fingerprint(params), now, now + ttlSeconds * 1000L);

        store.save(pending, Duration.ofSeconds(ttlSeconds));
        log.info("签发写确认令牌：session={} user={} order={} action={}",
                sessionId, userId, orderId, action);
        return pending.token();
    }

    public PendingWrite consume(String token, String sessionId, Long userId, String action,
                                Long orderId, Map<String, Object> params) {
        if (!StringUtils.hasText(token)) {
            throw invalidToken();
        }

        // 原子取出即删除；校验失败也不可重用
        PendingWrite pending = store.consume(token);
        if (pending == null) {
            throw invalidToken();
        }

        boolean sameOwner = Objects.equals(pending.sessionId(), sessionId)
                && Objects.equals(pending.userId(), userId)
                && Objects.equals(pending.action(), action)
                && Objects.equals(pending.orderId(), orderId);
        if (!sameOwner || pending.expiresAtMillis() <= System.currentTimeMillis()) {
            throw invalidToken();
        }
        if (!pending.paramsFingerprint().equals(fingerprint(params))) {
            throw new WriteRejectedException(409, "确认参数与预览不一致，请重新预览");
        }
        return pending;
    }

    // invalidToken / fingerprint / randomToken 保持 M4 实现
}
```

### 8.5 多实例时序：预览在 A，确认到 B

```
实例 A                                     Redis                        实例 B
  │ 预览 reviewWorkOrder(id=123)             │                             │
  ├─ 读项目一（熔断）                        │                             │
  ├─ SET agent:write:pending:TOK  EX 300 ──▶ │                             │
  │ 返回 PREVIEW（含 TOK）                   │                             │
  │                                          │  用户确认（请求落到 B）      │
  │                                          │ ◀── GETDEL agent:...:TOK ───┤
  │                                          │ ── 返回 PendingWrite ──────▶ │
  │                                          │                             ├─ 校验绑定/指纹
  │                                          │                             ├─ 权限 fresh
  │                                          │                             ├─ WriteGuard
  │                                          │                             └─ PUT 项目一
```

- **不需要粘性会话**：令牌在 Redis，任何实例都能消费。
- **重放**：第二次 `GETDEL` 返回 null → 409。
- **过期**：Redis TTL 自动删除；`consume` 拿到 null → 409。
- **跨用户 / 跨会话 / 换工单 / 换动作 / 改参数**：`PendingWrite` 里的绑定点逐项比对，仍然 409。

### 8.6 Redis 故障时写路径 fail-closed

| 操作 | Redis 正常 | Redis 挂了 |
|---|---|---|
| 预览（签发令牌） | 保存成功，返回 PREVIEW | `save` 抛 `WriteRejectedException(503)` → 工具返回 `{"code":503,...}`，**不产生任何写副作用** |
| 确认（消费令牌） | `GETDEL` 成功，继续写 | `consume` 抛 503 → 不写；用户稍后重新预览 |
| 重放 | null → 409 | 503（不是 409，明确是基础设施问题） |

> **绝不**在 Redis 故障时 fallback 到进程内 Map。那样会出现「A 实例签的令牌，B 实例不认」的分裂状态；写操作宁可不做。

### 8.7 `WriteGuard` 为什么保持进程内

`WriteGuard` 的键是 `traceId`，而 `traceId` 是**一次 HTTP SSE 请求**生成的；这次请求的所有工具调用都在同一台实例、同一条流上。它天生不需要跨实例共享。

- 如果强行放 Redis，每个工具调用多一次网络往返，收益为零。
- 10 分钟后自动清理的逻辑保持不变；它不涉及安全边界，只是「别在一轮里连写多张单」的限流。

### 8.8 令牌仍然不是「用户同意」的证明

M4 §7.1 的结论在 M5 不变：

- 令牌由 agent 在**模型发起预览时**签发，不需要用户参与；
- 模型完全可以自己预览、自己确认，不询问用户；
- Redis 只解决「多实例共享 + 一次性 + 过期」，不解决「模型假装用户同意」。

真正的安全边界仍是：项目一权限 + 数据范围 + 状态机、M2 的工具可见性、M4 的预览可读 + 每轮一次写 + 审计留痕。要做强确认，必须加前端确认通道，不在 M5。

### 8.9 本节的常见坑

1. **`getAndDelete` 不是所有 Redis 版本都有**（6.2+）；低版本用 Lua，别用「GET 再 DEL」两条命令。
2. **`PendingWrite` 反序列化失败要当「令牌无效」还是 503？** 如果是 Redis 里数据损坏，当 503 更诚实；如果是格式不兼容，重新预览即可。本文的实现把 JSON 异常统一成 503，避免误放行。
3. **`isFull` 只对进程内实现有效**。Redis 模式下 `max-preview-entries` 被忽略，靠 300 秒 TTL 收敛；这是有意的，不要跨实例 `SCAN` 数令牌。
4. **perms 缓存 key 只放 SHA-256**。不要为了排查方便把明文 token 写进 key 或 value。
5. **写确认前重查权限**：先查 fresh 权限，再消费令牌；这样权限被收回时令牌不会被白白烧掉。

## 九、审计保留、指标与健康检查

### 9.1 审计表会无限膨胀，而且当前缺一个索引

`agent_tool_call_log` 是只增不改的表。M2 已经预见「长期膨胀」（R11），M5 兑现清理。先看一个容易被忽略的细节：

当前索引是：

```sql
KEY `idx_session`   (`session_id`),
KEY `idx_user_time` (`user_id`, `create_time`),
KEY `idx_tool_time` (`tool_name`, `create_time`)
```

清理 SQL 是 `WHERE create_time < ?`。MySQL **无法**用 `(user_id, create_time)` 或 `(tool_name, create_time)` 的最左前缀之外的列做范围扫描；所以这条 SQL 会全表扫描。M5 必须补一个单列索引：

```sql
ALTER TABLE `agent_tool_call_log`
  ADD KEY `idx_create_time` (`create_time`);
```

### 9.2 保留策略

| 配置 | 默认 | 说明 |
|---|---|---|
| `agent.audit.retention-enabled` | true | 开关；压测 / 排障时可关 |
| `agent.audit.retention-days` | 90 | 保留天数；`<=0` 表示不清理 |
| `agent.audit.retention-cron` | `0 30 3 * * *` | 每天 03:30（Spring 6 段 cron，含秒） |
| `agent.audit.retention-batch-size` | 1000 | 每批删除行数，避免长事务 / 大 binlog |
| `agent.audit.retention-max-batches` | 20 | 单次任务最多删 2 万行，避免一次跑太久 |

> 为什么按批删：一次性 `DELETE` 几十万行会长时间持锁、生成巨大 binlog、拖慢主库。分批删把影响摊平，失败了下次还能继续。
>
> 为什么不用分区表：按天分区要改表结构、要维护分区创建/删除，收益是「秒删」，但本项目量级用不上；批删 + 索引足够。

```java
package com.agentworkorder.audit;

import com.agentworkorder.audit.mapper.AgentToolCallLogMapper;
import com.agentworkorder.config.AuditProperties;
import lombok.extern.slf4j.Slf4j;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;

@Slf4j
@Component
@ConditionalOnProperty(name = "agent.audit.retention-enabled", havingValue = "true", matchIfMissing = true)
public class AuditRetentionJob {

    private final AgentToolCallLogMapper mapper;
    private final AuditProperties properties;

    public AuditRetentionJob(AgentToolCallLogMapper mapper, AuditProperties properties) {
        this.mapper = mapper;
        this.properties = properties;
    }

    @Scheduled(cron = "${agent.audit.retention-cron:0 30 3 * * *}")
    public void purgeExpired() {
        int days = properties.getRetentionDays();
        if (days <= 0) {
            return;
        }
        LocalDateTime cutoff = LocalDateTime.now().minusDays(days);
        int batchSize = Math.max(1, properties.getRetentionBatchSize());
        int maxBatches = Math.max(1, properties.getRetentionMaxBatches());

        int total = 0;
        for (int i = 0; i < maxBatches; i++) {
            int deleted = mapper.deleteOlderThan(cutoff, batchSize);
            total += deleted;
            if (deleted < batchSize) {
                break;
            }
        }
        if (total > 0) {
            log.info("审计清理完成：cutoff={} 删除 {} 行", cutoff, total);
        }
    }
}
```

### 9.4 清理任务的时区与多实例

- `LocalDateTime.now()` 用的是 JVM 时区；MySQL `DATETIME` 不带时区。**确保应用容器与数据库使用同一时区**，否则「90 天」会偏几个小时。建议部署时固定 `TZ=Asia/Shanghai`。
- 多实例同时跑清理任务不会造成错误：`DELETE ... WHERE create_time < ? LIMIT ?` 是幂等的，两个实例最多是「一个删了、另一个删 0 行」。如果要严格单实例执行，可以后续加 ShedLock；M5 不引入。

### 9.5 指标：只做能指导动作的几个

M5 不追求「每个方法一个指标」，只做能回答下面问题的几个：

| 指标 | 类型 | 标签 | 回答什么问题 |
|---|---|---|---|
| `agent.circuit.open` | Gauge 0/1 | `resource` | 现在哪个下游被熔断了？ |
| `agent.circuit.rejected` | Counter | `resource` | 熔断拒绝了多少请求？ |
| `agent.circuit.failures` | Counter | `resource` | 下游失败率大概多少？ |
| `agent.sse.errors` | Counter | `code` | 客户端看到的错误类型分布 |
| `agent.write.actions` | Counter | `action` / `mode` / `result` | 预览 / 确认 / 失败各多少？ |

### 9.6 健康检查：别把「可降级依赖」放进 readiness

```java
package com.agentworkorder.metrics;

import com.agentworkorder.resilience.ResilienceGuard;
import org.springframework.boot.actuate.health.Health;
import org.springframework.boot.actuate.health.HealthIndicator;
import org.springframework.data.redis.core.RedisCallback;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.util.LinkedHashMap;
import java.util.Map;

/**
 * 依赖健康：熔断状态 + Redis 连通性。
 *
 * <p>返回自定义状态 DEGRADED（HTTP 仍 200），用于「能服务、但部分能力降级」；
 * 不要把它直接塞进 readiness，否则 Redis 一挂所有实例都被摘掉，反而全站不可用。
 */
@Component
public class AgentDependenciesHealthIndicator implements HealthIndicator {

    private final ResilienceGuard guard;
    private final StringRedisTemplate redis;

    public AgentDependenciesHealthIndicator(ResilienceGuard guard, StringRedisTemplate redis) {
        this.guard = guard;
        this.redis = redis;
    }

    @Override
    public Health health() {
        Map<String, Object> details = new LinkedHashMap<>();
        Map<String, String> circuits = guard.states();
        details.put("circuits", circuits);

        boolean redisUp;
        try {
            String pong = redis.execute((RedisCallback<String>) connection -> connection.ping());
            redisUp = "PONG".equalsIgnoreCase(pong);
        } catch (Exception e) {
            redisUp = false;
        }
        details.put("redis", redisUp ? "UP" : "DOWN");

        boolean degraded = !redisUp || circuits.containsValue("OPEN");
        Health.Builder builder = degraded ? Health.status("DEGRADED") : Health.up();
        return builder.withDetails(details).build();
    }
}
```

readiness / liveness 的建议：

| 组 | 包含 | 理由 |
|---|---|---|
| liveness | `livenessState`, `ping` | 只判断「进程还活着」，不要依赖任何外部组件 |
| readiness | `readinessState` | 是否愿意接流量；**不要**包含 Redis / 项目一，因为它们是可降级依赖 |
| 自定义 `agentDependencies` | 熔断 + Redis | 给运维看细节、配告警；不参与摘流 |

### 9.7 告警建议

| 告警 | 条件 | 动作 |
|---|---|---|
| 下游熔断 | `agent.circuit.open{resource=...} == 1` 持续 1 分钟 | 看下游健康、看日志 |
| SSE 错误率高 | `rate(agent.sse.errors[5m])` 明显上升 | 看是 502 还是 504，区分模型 / 网络 |
| 写操作失败 | `agent.write.actions{result="ERROR"}` 上升 | 看审计表 `result_code` |
| 审计写入失败 | 日志关键字「审计写入失败」 | 查 MySQL 连接池 / 表空间 |
| Redis 降级 | 日志「读取会话记忆失败」「perms 缓存失败」 | 查 Redis；短时可接受，长时要修 |
| 审计表过大 | `SELECT COUNT(*)` 超阈值 | 检查清理任务是否执行、保留期是否合理 |

### 9.8 日志规范

- 每轮对话：`trace=... session=... user=... provider=... visibleTools=N`（M1 已有类似日志，保留）。
- 每次工具调用：`tool=... latency=... status=...`（审计表已有，日志只需简短一行）。
- **不要打印**：完整 JWT、完整 `confirmationToken`、完整工具返回体（可能含业务明细）。
- 错误日志打完整堆栈，但 SSE 的 `data` 只给脱敏后的一句话。
- Redis 降级日志用 `warn`，不要用 `error` 刷屏；同一个故障可能每轮都触发。

### 9.9 本节的常见坑

1. **`@Scheduled` 不生效**：忘记在启动类加 `@EnableScheduling`，任务永远不会跑。
2. **cron 是 6 段**（秒 分 时 日 月 周），不是 Linux 的 5 段；`0 30 3 * * *` 是每天 03:30:00。
3. **`LIMIT #{limit}` 在 MySQL 可用**，但某些数据库（如旧版 Oracle）不支持；本项目只跑 MySQL。
4. **删除条件没有索引会全表扫描**：先加 `idx_create_time`，再上线任务。
5. **Actuator 的 `show-details: always` 会暴露内部信息**：生产环境要么只在内网开放，要么配合安全组件用 `when_authorized`。

| **R40** | Redis 单点故障 | M5 按可降级设计：记忆失、perms 回源、写 fail-closed；高可用交给运维（主从 / 哨兵） |
| **R41** | Spring AI 1.1.2 没有官方 Redis ChatMemoryRepository | 自写约 100 行适配器；将来升级到 2.x 有官方实现时可替换，`ChatMemory` 层不变 |
| **R42** | 只存文本、不存 tool 消息，跨轮工具上下文丢失 | 刻意取舍：实时数据每轮重查；避免孤儿 tool 消息导致提供方 400 |
| **R43** | 同一会话并发请求「后写覆盖先写」 | 与内存版行为一致；M5 不加分布式锁；需要更强一致性时按会话串行化 |
| **R44** | Redis 淘汰 / 丢失写令牌 | `volatile-lru` + 写路径 fail-closed；令牌丢了就重新预览，不会误写 |
| **R45** | SSE 协议 v2 对旧前端是破坏性新增 | token 帧保持无名；done/error 命名事件；前后端一起上线，或先用开关只开心跳 |
| **R46** | `Flux.merge` + `takeUntil` 的心跳写法有细节坑 | 按 §6.3 的 `concatWith` + `onErrorResume` 顺序实现；用慢流 / 错误流各测一次；必要时退回 `SseEmitter` |
| **R47** | 熔断器是每实例独立，不是集群级 | 每实例自保已经能防止「所有实例一起等死」；要集群级再上 Sentinel |
| **R48** | 连续失败阈值在低流量下可能「一次抖动就打开」 | 阈值 5 + 30 秒半开；可调；不要把它当成精确的失败率 |
| **R49** | Reactor `timeout` 不能中断阻塞中的工具调用 | 项目一用 HTTP 超时；Milvus 用 SDK 超时；Reactor 超时只保证客户端能收到错误 |
| **R50** | 审计批量删除仍有锁 / binlog 压力 | 小批量 + 低峰 + 索引；避免一次删太多 |
| **R51** | 恶意超长 / 特殊字符 sessionId 制造大量 Redis key | controller 正则校验 + TTL + 网关限流；不要只靠 Redis |
| **R52** | 令牌 / perms 值落 Redis，运维可读 | 不存明文 JWT；令牌短命且一次性；Redis 加 ACL / 密码，限制访问 |
| **R53** | `@Scheduled` 多实例重复执行 | `DELETE ... LIMIT` 幂等；重复跑最多删 0 行；需要严格单实例再加 ShedLock |
| **R54** | 指标标签基数爆炸 | 固定标签（resource / action / mode / result / code），绝不加 sessionId/userId/traceId |
| **R55** | 把 Redis 放进 readiness 导致「Redis 挂 → 全站摘流」 | readiness 只包含 `readinessState`；Redis 放自定义 `agentDependencies` 详情 |
| **R56** | 记忆键加 userId 后，老会话（纯 sessionId）在新版本读不到 | 部署后旧内存/旧 key 自然失效；记忆不是业务数据，可接受 |
| **R57** | Actuator 暴露 metrics / health 细节 | 内网 / 网关限制；生产用 `when_authorized` + 安全组件 |
| **R58** | `spring.data.redis.timeout=2000` 对慢网络可能偏短 | 本地 / 同机房 2s 足够；跨机房可调到 3-5s，但不要回到 10s |

## 十四、我们没选什么

| 备选 | 为什么不选 |
|---|---|
| **默认上 Sentinel** | 能力过剩：M5 只需要「下游挂了别一直打」，不需要控制台 / 集群流控；依赖与版本对齐、规则配置、`SphU.entry` 手工埋点都不适合「手写一遍就懂」。附录 B 保留等价接法 |
| **Resilience4j** | 仍是新依赖；注解 AOP 对内部调用失效；两套 fallback 的定制不如自己写直观 |
| **官方 Redis ChatMemoryRepository** | 1.1.2 没有；升级到 2.x 是另一件事，不能为了一个存储换整个 Spring AI 大版本 |
| **直接序列化 Spring AI `Message` 到 Redis** | 多态、tool call、metadata 结构复杂；升级易坏；只存 `role + text` 更稳 |
| **会话记忆不区分用户** | 会造成跨用户历史泄漏（§2.7），必须加 userId |
| **把写令牌也放进程内，靠粘性会话** | 负载均衡一换实例就失效；重启即丢；粘性会话还会让发布 / 扩容变复杂 |
| **Redis 故障时把令牌降级到进程内 Map** | 会出现「A 签、B 不认」的分裂；写操作宁可不做 |
| **工具结果缓存到 Redis** | 工单数据有时效性与数据范围；缓存会制造旧数据 / 越权风险 |
| **JWT 存 Redis** | 只需要 SHA-256 做缓存 key；明文 token 不落任何存储 |
| **自动重试读 / 写** | 读重试放大下游压力；写重试可能重复流转；M4 已明确不自动重试 |
| **把 Redis 放进 readiness** | Redis 是可降级依赖；放进去会导致 Redis 一挂全站摘流，反而扩大故障 |
| **一次性 `DELETE` 全部过期审计** | 长事务、大 binlog、锁表；分批更稳 |
| **审计表按天分区** | 量级没到；分区维护成本高于收益 |
| **SSE 改 POST + 消息队列** | 改变交互模型，前端要重写；M5 只做协议收口 |
| **用 `KEYS` 扫会话** | 阻塞 Redis；用 `SCAN` |
| **把 `WriteGuard` 也搬 Redis** | 一轮对话只在一台实例上，搬过去只增加一次网络往返，收益为零 |

### 手写时最容易编译不过的 5 个地方

## 附录 B：如果必须用 Sentinel（等价接法）

> 这一节不是 M5 的默认方案，只是给「答辩 / 简历要求出现 Sentinel」的场景一个**不推翻 §7 设计**的接法。

### B.1 依赖

```xml
<dependency>
  <groupId>com.alibaba.csp</groupId>
  <artifactId>sentinel-core</artifactId>
  <version>1.8.8</version>
</dependency>
<dependency>
  <groupId>com.alibaba.csp</groupId>
  <artifactId>sentinel-annotation-aspectj</artifactId>
  <version>1.8.8</version>
</dependency>
```

（要控制台再加 `sentinel-transport-simple-http` 与 Dashboard；M5 不需要。）

### B.2 把 `ResilienceGuard.call` 换成 `SphU.entry`

```java
public <T> T call(String resource, Supplier<T> action,
                  Supplier<T> whenOpen, Function<RuntimeException, T> whenFailed) {
    try (Entry entry = SphU.entry(resource)) {
        try {
            return action.get();
        } catch (RuntimeException e) {
            Tracer.traceEntry(e, entry);   // 让 Sentinel 统计异常
            return whenFailed.apply(e);
        }
    } catch (BlockException e) {
        // 被流控 / 熔断规则拦截：请求没有真正发出去
        return whenOpen.get();
    }
}
```

### B.3 熔断规则（等价于 §7.3 的参数）

```java
DegradeRule rule = new DegradeRule("project-one");
rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO); // 异常比例
rule.setCount(0.5);                 // 50%
rule.setMinRequestAmount(5);        // 至少 5 个请求才统计
rule.setStatIntervalMs(10_000);     // 10 秒统计窗口
rule.setTimeWindow(30);             // 熔断 30 秒
DegradeRuleManager.loadRules(List.of(rule));
```

> 具体 API 以你引入的 Sentinel 版本为准；核心语义与 §7.3 一致：阈值、统计窗口、熔断时长、半开试探。
>
> **注意**：Sentinel 的 `@SentinelResource` 走 AOP，**类内部自调用不会生效**；本项目建议直接用 `SphU.entry` 包在 `ResilienceGuard` 里，避免代理陷阱。

### B.4 与本文方案的关系

| 本文 | Sentinel 等价物 |
|---|---|
| `CircuitBreaker` 三态 | `DegradeRule` 熔断规则 |
| `ResilienceGuard.call` | `SphU.entry(resource)` + `BlockException` |
| `whenOpen` | `BlockException` 分支 |
| `whenFailed` | 业务异常分支 + `Tracer.traceEntry` |
| `states()` / 指标 | Dashboard 或 `ClusterNode` 指标 |

业务代码只依赖 `ResilienceGuard`；换 Sentinel 时只改它的实现，工具与 controller 不动。

## 附录 C：与其它里程碑的衔接

| 里程碑 | 与 M5 的关系 |
|---|---|
| ✅ M1 | 保留 `LlmClient` 端口 / SSE / 工具；M5 只给端口加一个 `traceId` 参数，给 SSE 加协议收尾 |
| ✅ M2 | 审计表、工具可见性、`PermService` 全部保留；M5 只把 perms 缓存换成 Redis，并加写前 fresh 校验 |
| ✅ M3 | RAG 工具与检索逻辑不变；M5 只加熔断与超时，不让知识库故障拖垮工单问答 |
| ✅ M4 | 两阶段确认、令牌绑定、每轮一次写全部保留；M5 把令牌存储换成 Redis，解决多实例与重启丢失 |
| 前端 | 需要同步 SSE v2：识别 `done` / `error` / 心跳；`fetch` 解析示例见 §6.5 |
| 运维 | 需要 Redis（db5）与审计清理任务；建议配 `volatile-lru`、固定时区、网关关闭 SSE 缓冲 |
| 下一阶段（若要继续） | RAG Rerank、分布式追踪、`POST /chat`、前端强确认通道、Sentinel 集群规则 |

**分层原则**：M5 不新增业务能力，只给 M1–M4 的主干加「持久化、收尾、熔断、清理」四层保护。每一层都有独立开关；任何一层出问题，都能退回上一层的完整行为。
