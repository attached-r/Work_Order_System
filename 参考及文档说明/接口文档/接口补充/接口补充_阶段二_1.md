## 1. 后端已交付部分

> 以下契约均与新版 `openapi.json` 核对一致。**注意 `@RequiresPermission` 不会出现在 OpenAPI 里**(自定义注解,非标准 security scheme),所以权限要求是从后端源码确认的,不是从文档读的。

### 补充-1 ✅ 角色已分配权限

新增只读接口,与覆盖式写接口配对,**先读后写**:

#### `GET /role/{roleId}/permissions`

| 项 | 值 |
| --- | --- |
| operationId | `listPermissions` |
| 权限 | `user:manage` |
| 响应 | `ResultListLong` — `data` 为该角色已绑定的**权限ID列表**,无权限时为空数组 |

与本文原提案完全一致:只回 ID,**不回 `PermissionVO`** —— 权限名称由前端用 `GET /permission/tree` 的字典自行映射。

**前端接入后即可删除三处防护**:角色页顶部 `el-alert`、抽屉内 `el-alert`、以及保存前那个"将清空该角色全部权限"的二次确认。

### 补充-3 ✅ 用户 / 部门只读目录

两个接口都**刻意不挂 `@RequiresPermission`** —— 登录即可访问,拦截器仍校验 token:

#### `GET /user/directory`

| 项 | 值 |
| --- | --- |
| operationId | 见 openapi(用户目录) |
| 权限 | 仅需登录 |
| 响应 | `ResultListUserBriefVO` |

`UserBriefVO` 字段(**与提案完全一致**):`userId` / `username` / `realName` / `departmentId` / `departmentName` / `status` / `roles`。

Schema 描述直接写着「用户只读目录项(**不含权限码**)」—— 这正是提案里的关键要求:避免普通账号枚举全量用户及其权限清单。`roles` 保留,派单下拉靠它筛 `HANDLER` 候选。

#### `GET /department/directory`

| 项 | 值 |
| --- | --- |
| 权限 | 仅需登录 |
| 响应 | `ResultListDepartmentBriefVO` |

`DepartmentBriefVO`:`id` / `deptCode` / `deptName` —— 已按提案去掉 `remark` / `createTime`。

**两个额外收获(超出原提案,前端可直接受益):**

1. **`listDirectory()` 是全查不分页的**(`selectList(orderByAsc(id))`),没有 500 行上限。原「部门人数在前端聚合、超过 500 行会被静默截断」的问题**因此消失** —— 见补充-6。
2. **`UserBriefVO` 自带 `departmentName`**,所以用户管理页解析部门名不再需要部门目录,一个用户目录就够了。

### 补充-4 ✅ `UserVO.phone` 回读

`UserVO` 新增 `phone`,描述为「联系电话,未填写时为空」。`/user/page` 与 `/user/me` 同时生效。

清空语义**采纳了本文的「方案 i」**,并写进了 `UpdateUserDTO` 的 Schema 描述:

> `phone` — 联系电话;**传空字符串表示清空,不传(null)表示不修改**

后端实现(`UserService.updateUser`)还会 `trim()`,所以 `"   "` 这类纯空白同样被当作清空,不会存成有效值。

**⚠️ 一处集成细节需要前端注意:** 清空时写入的是**空字符串 `''` 而非 `NULL`**。所以前端判「未填写」要同时覆盖 `''`、`null`、`undefined` 三种,不能只判 `== null`,否则清空后编辑框会显示出 `''` 被当成"有值"。

### 补充-5 ✅ `/user/page` 筛选参数

新增三个**可选**查询参数,全空时行为与旧版完全一致:

| 参数名 | 类型 | 说明 |
| --- | --- | --- |
| `departmentId` | integer/int64 | 按所属部门筛选 |
| `status` | integer/int32 | 按状态筛选:1启用 0停用 |
| `roleCode` | string | 按角色标识筛选,如 `HANDLER` |

三个都做了(含实现成本最高的 `roleCode`),用户管理页的部门筛选器可以恢复。

## 3. 已确认不做 / 待定

### 补充-2 ⛔ 工单原地编辑 —— 已确认不做

**原提案:** 新增 `PUT /workorder/{id}`,允许提单人在**待审核(0)**状态下原地修改工单内容。

**结论:不做,且这是明确的设计决定,不是遗漏。**

确定的业务规则:

> **工单一旦提交即不可修改。** 内容要改,只有两条路:
> - **被驳回(5)** → 提单人走 `POST /workorder/{id}/resubmit`(需 `workorder:modify`)修改并重投,状态回到 待审核(0);
> - **超时(7)** → 工单终态关闭,提单人**重新提单**(新工单、新编号)。

两点补充说明:

1. **超时后不能 resubmit。** `TRANSITIONS[7] = []`,已超时是终态;`resubmit` 内部走 `transition(order, PENDING_REVIEW, ...)` 会校验 `5→0`,从 7 出发必然失败。所以超时后确实是"重新提单",和驳回后的"重投"不是一回事。
2. **这样设计是对的,我原先的提案是错的。** 原提案里我自己也写了「不要把编辑做成 0→0 自迁移」,但那其实是在给一个本身就有问题的需求找实现方式 —— 只要有"不改变状态的写操作",就存在一条**绕开状态机的修改路径**。直接不提供编辑接口,才能保证「流转记录只由状态迁移产生」这个不变量(与 §八 Q1「状态只能通过业务动作改变,无法被直接赋值」同源)。

该规则已写入 `backend/设计理念/工单核心业务.md` §七 的接口清单下方,与本文互相引用。

**前端状态:** 已按此调整完毕 —— 详情页的「修改」动作(`edit`)已从 `src/constants/workorder.ts` 的 `WorkOrderAction` 联合类型中删除,待审核状态下提单人只剩「撤回」。**这一项不再需要任何前端改动。**

### 补充-6 ⬜ 部门人数

**未做,但影响已基本消失。** 原问题是前端从 `/user/page` 拉 500 行自己 `filter().length`,超出后人数封顶不准。

`GET /user/directory` 修好之后,前端可以从**全量不分页**的目录算人数,结果精确,不再需要后端提供 `userCount`。

**剩下的唯一代价**是把全量用户拉到前端算一个数字。数据量小的时候这是零成本;如果用户数上千,再考虑让 `/department/list` 带 `userCount`(或在目录接口里加)。**当前建议:不做。**

### 补充-7 ⬜ 注册页部门选项

**未做,建议维持现状(原「方案 i」)。** 新注册账号本来就需要管理员分配角色,部门一并分配是更一致的流程;为注册页开一个免登录的部门枚举接口并不值得。`RegisterDTO.departmentId` 仍是可选的,不传也能注册成功。

**前端状态:** 注册页的部门选择器已删除、改为文案说明,**不需要再改**。

## 4. 三个确认项

### 确认-1 ✅ 部门不可清空 —— 是设计,非缺陷

`AssignDepartmentDTO.departmentId` 上的 `@NotNull` **有意为之,保持不变**。

部门是权限与数据隔离的基础维度,`WorkOrderService` 多处依赖,**部门为空的账号会直接残废**:

| 位置 | 部门为空时 |
| --- | --- |
| `create()` | 抛「当前用户未归属部门,无法提交工单」 |
| `requireViewScope()` | 审核人 / 派单人**看不到本部门工单** |
| `requireDepartmentScope()` | 抛「无权操作其他部门的工单」→ 无法审核 / 派单 |
| `requireTransferScope()` | 抛「无权转派该工单」 |

**前端已按此实现:** 部门弹窗的下拉框刻意不可清除(`clearable` 关闭),提示文案说明了原因。要停用某人请走 `PUT /user/{userId}/status`。

> 建议(可选):把原因写进 `@Schema` 描述,例如「部门不能为空:部门是工单数据隔离的基础」,免得后来者误以为是漏写的 `@NotNull` 而顺手放开。

### 确认-2 ⬜ 权限树种子数据缺层级

`PermissionService.tree()` 的实现是**正确的** —— 按 `parentId` 装配树,还处理了"父节点不存在时降级为一级权限"的脏数据兜底。

问题是**数据**:`db/data.sql` 第 37 行的插入语句只写了 `(perm_code, perm_name)`,没有 `parent_id` 列,所以 10 行全是 `NULL`:

```sql
INSERT INTO work_order_system.permission  (`perm_code`, `perm_name`)
VALUES ('workorder:create', '提交工单'),
       ...
       ('user:manage', '用户/角色/部门管理');
```

**已验证:** `GET /permission/tree` 返回 10 个一级节点,全部 `parentId: null`。

**当前处理:** 前端按 `permCode` 的冒号前缀自己分组(`workorder` / `user`),组名用前端硬编码映射表,并做了兜底 —— 任何未知前缀落入「其它」分组,**新增权限码不会被静默丢弃**。

**建议(优先级低):** 若希望组名由后端定义,在种子数据里补两个纯分组用的父权限行(`工单管理` / `系统管理`)。届时需要明确**父权限行本身是否算一条真实权限**,否则会出现"分了个空壳权限给角色"。当前状态可用,不急于改。

### 确认-3 ⏳ 时间参数必须 `T` 分隔

**已验证:** 传 `2026-09-14 20:49:24`(空格)→ `400 请求参数格式错误`;传 `2026-09-14T20:49:24` → 正常。

**建议:** 在主文档 `智能工单系统 API.md` 的 `date-time` 字段说明里明确写出格式 `yyyy-MM-dd'T'HH:mm:ss`,并在开头「OAS 不完整导出」那类提示里补一句"不接受空格分隔"。**这是文档待办,不是代码问题。**

**前端状态:** 已收敛到 `src/utils/datetime.ts` 的 `toIsoLocal()` / `parseTime()`,业务代码不自己拼字符串,**无需再改**。
