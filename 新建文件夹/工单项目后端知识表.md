## 1. 项目概览

### 1.1 业务场景

这是一个企业内部「工单资源管理平台」的后端，核心业务是：

```
提单人提交工单 → 本部门审核人审核 → 派单人派单 → 处理人处理 → 提单人验收
                    ↓ 驳回                    ↓ 转派/返工
                 修改后重提                仍在「处理中」
```

围绕主流程，还实现了：

- **RBAC 权限模型**：部门、用户、角色、权限、用户-角色、角色-权限；
- **数据范围隔离**：不同角色只能看到自己 / 本部门 / 指派给自己的工单；
- **状态机**：所有状态变更统一校验，非法迁移返回业务冲突；
- **异步通知**：工单流转后给相关人发站内信，要求消息不丢、不重复；
- **缓存与分布式锁**：登录态、鉴权快照、工单详情、权限字典、编号生成、资源申请互斥；
- **Agent 工具接口**：`/tool/**` 供另一个 Agent 项目通过 OpenFeign 调用，返回裸业务对象。

### 2.2 各层职责

| 层 | 代表类 | 职责 | 不该做的事 |
|---|---|---|---|
| Controller | `WorkOrderController` | 接收 HTTP、绑定参数、`@Valid` 校验、挂权限注解、把 Service 结果包成 `Result` | 写业务逻辑、直接操作 Mapper |
| Service 接口 | `IWorkOrderService` | 定义业务能力，供 Controller 与其他 Service 依赖 | 暴露实现细节 |
| Service 实现 | `WorkOrderService` | 业务规则、状态机、事务、缓存、锁、MQ 意图 | 处理 HTTP 细节 |
| Mapper | `WorkOrderMapper extends BaseMapper<WorkOrder>` | 单表 CRUD + 少量手写 SQL | 写业务判断 |
| POJO | `WorkOrder` | 与数据库表一一映射 | 直接作为接口出入参 |
| DTO | `WorkOrderCreateDTO` | 接收请求参数 + 校验注解 | 带数据库字段（如 `version/deleted`） |
| VO | `WorkOrderDetailVO` | 返回给前端/Agent 的视图 | 暴露密码、内部字段 |
| Enum | `WorkOrderStatus` | 状态码、迁移规则、中文描述 | 散落魔法数字 |

### 2.3 接口与实现

项目采用「接口 + 实现」的方式：

```java
public interface IWorkOrderService {
    Long create(WorkOrderCreateDTO dto);
    WorkOrderDetailVO detail(Long id);
    // ...
}

@Service
@RequiredArgsConstructor
public class WorkOrderService implements IWorkOrderService {
    private final WorkOrderMapper workOrderMapper;
    // ...
}
```

Controller 只依赖接口：

```java
@RestController
@RequestMapping("/workorder")
@RequiredArgsConstructor
public class WorkOrderController {
    private final IWorkOrderService workOrderService;
}
```

依赖注入方式统一为 **构造器注入**：类上加 Lombok `@RequiredArgsConstructor`，把依赖声明为 `private final`。好处：

- 依赖不可变，避免运行期被替换；
- 缺依赖时启动即失败，不会出现 `NullPointerException`；
- 便于单元测试直接 `new` 或传 mock。

> 说明：`IUserService#login` / `register` 返回的是 `Result<T>`，而其他 Service 方法返回领域对象或 `void`。这是项目演进中留下的小不一致：多数情况下 Service 不应感知 `Result`，Controller 负责包装。阅读时知道即可，新接口建议统一为「Service 返回业务对象，Controller 包 `Result`」。

### 2.4 依赖方向

```text
Controller → Service 接口 → Service 实现 → Mapper → MySQL
                                   ├→ CacheClient → RedisTemplate / RedisLockHelper
                                   ├→ NotifyOutboxWriter → outbox 表 + 事件
                                   └→ 其他 Mapper / Service
```

约束：

- Controller 不直接依赖 Mapper；
- Mapper 不依赖 Service；
- 工具类（`JwtUtil`、`PasswordUtil`）无业务状态；
- 横切能力（鉴权、异常、缓存、锁、MQ）各自收敛到专门组件。

### 3.2 application.yaml 速查

| 配置段 | 关键值 | 说明 |

### 3.3 核心配置类

#### WebMvcConfig

`config/WebMvcConfig.java` 注册 `LoginInterceptor`：

- 拦截 `/**`；
- 放行：`/user/login`、`/user/register`、`/doc.html`、`/webjars/**`、`/v3/api-docs/**`、`/swagger-ui/**`、`/favicon.ico`。

除这些路径外，所有接口（包括 `/notification/**`、`/tool/**`）都要求登录。

#### MybatisPlusConfig

`config/MybatisPlusConfig.java`：

```java
interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
```

- 没有乐观锁插件，`@Version` 不生效；
- 没有分页插件，`selectPage` 会退化成全表查询。

#### RedisConfig

`config/RedisConfig.java`：

- key / hash key：`StringRedisSerializer`；
- value / hash value：`GenericJacksonJsonRedisSerializer`；
- 通过 `activateDefaultTypingAsProperty(..., "@class")` 写入类型信息，保证反序列化能还原成具体类；
- 使用 Jackson 3（`tools.jackson`），不是 Jackson 2（`com.fasterxml.jackson`）。

#### RedissonConfig

`config/RedissonConfig.java` 手工创建 `RedissonClient`：

- 只用核心包，不用 `redisson-spring-boot-starter`：
  - 避免 starter 的 `spring-data-redis` 适配版本与 Boot 4 不匹配；
  - 避免 starter 接管 `RedisTemplate`、改变既有序列化格式。
- 复用 `spring.data.redis.*` 连接参数；
- `config.setCodec(StringCodec.INSTANCE)`：锁值只是线程标识，不参与 Jackson 序列化；
- `@Bean(destroyMethod = "shutdown")`：容器关闭时释放连接与后台线程。

#### RabbitMqConfig

`config/RabbitMqConfig.java` 声明：

- Topic 交换机 `workorder.notify.exchange`；
- 持久队列 `workorder.notify.queue`，绑定 `workorder.notify.#`；
- 队列挂死信参数：`x-dead-letter-exchange = workorder.notify.dlx`、`x-dead-letter-routing-key = workorder.notify.dead`；
- Direct 死信交换机与 DLQ；
- `JacksonJsonMessageConverter(NotifyMessage.jsonMapper())`。

**刻意不声明 `RabbitTemplate` / `RabbitAdmin`**：它们由 Boot 自动配置创建，并读取 `publisher-confirm-type`、`publisher-returns`、`template.mandatory`。手写会静默丢掉这些设置。

整个配置类受 `@ConditionalOnProperty(prefix = "mq.notify", name = "enabled", havingValue = "true")` 门控。

#### CacheConfig

`config/CacheConfig.java` 提供 `cacheRebuildExecutor`：

- 核心 2、最大 4、队列 256；
- 拒绝策略是「丢弃 + warn」，不是 `CallerRunsPolicy`——缓存重建是可丢弃的优化，不能把压力回灌给请求线程。

#### OpenApiConfig

`config/OpenApiConfig.java` 定义全局文档与多个分组：用户、部门、角色、权限、工单、通知。

> 注意：`AgentToolOpenApi()` 里 `pathsToMatch("/AgentTool/**")` 与实际接口 `/tool/**` 不一致，且 group 名重复为「通知中心」。这是当前代码的小瑕疵，不影响业务接口；若要看 Agent Tool 文档，按实际路径访问即可。

### 3.4 配置绑定

三个 `@ConfigurationProperties` 类把「策略参数」从代码里抽出来：

| 类 | 前缀 | 内容 |
|---|---|---|

### 4.1 Result

```java
    private Long timestamp;
```

```json

  "message": "success",

```

失败响应示例：

```json
{
  "code": 401,
  "message": "登录已失效,请重新登录",
  "data": null,
  "timestamp": 1760000000000
```

### 4.2 ResultCode

`common/ResultCode.java`：

| 枚举 | code | message | 典型场景 |
|---|---|---|---|
| `SUCCESS` | 200 | success | 正常 |
| `BAD_REQUEST` | 400 | 参数错误 | 参数校验失败、非法 ID |
| `UNAUTHORIZED` | 401 | 未登录或已过期 | 无 token、token 失效、用户被删 |
| `FORBIDDEN` | 403 | 无权限 | 权限码不足、数据范围不符 |
| `NOT_FOUND` | 404 | 数据不存在 | 工单/用户/角色/通知不存在 |
| `CONFLICT` | 409 | 业务冲突 | 状态机非法、乐观锁冲突、重复申请 |
| `INTERNAL_SERVER_ERROR` | 500 | 系统异常，请稍后再试 | 未捕获异常 |

**关键约定：HTTP 状态码恒为 200，真实业务状态看响应体的 `code`。**

这样做的好处是前端只需一套响应拦截逻辑；代价是不能直接利用 HTTP 语义做缓存、网关策略。项目统一选择了前者。

```java
    private long current;
    private long size;
```

与 MyBatis-Plus 的 `Page<T>` 对应，但只暴露前端需要的四个字段。

### 4.4 BusinessException

`exception/BusinessException.java`：

- 继承 `RuntimeException`，携带 `Integer code`；
- 默认业务码为 `409`；
- Service 主动抛出的业务错误都用它，例如：

```java

```

### 4.5 GlobalExceptionHandler

`exception/GlobalExceptionHandler.java` 使用 `@RestControllerAdvice`，把异常统一转成 `Result<Void>`：

| 捕获异常 | 返回 |
|---|---|
| `BusinessException` | 使用异常自带的 `code` / `message` |
| `MethodArgumentNotValidException` | 400，第一条字段错误 `field: message` |
| `BindException` | 400，同上 |
| `ConstraintViolationException` | 400，第一条约束错误 |

### 4.6 ToolExceptionHandler

`exception/ToolExceptionHandler.java`：

```java
@Order(Ordered.HIGHEST_PRECEDENCE)
@RestControllerAdvice(basePackages = "com.rj.controller.tool")
public class ToolExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public ToolErrorVO handleBusinessException(BusinessException e) {

```

特点：

- 只作用于 `com.rj.controller.tool` 包，普通接口仍走 `GlobalExceptionHandler`；

| 接口类型 | 成功响应 | 失败响应 |

| Agent Tool 接口 | 直接返回业务对象，如 `PageResult<WorkOrderVO>`、`UserVO` | `ToolErrorVO {code, message}` |

## 5. 认证与鉴权

### 5.1 登录流程

入口：`POST /user/login` → `UserController#login` → `UserService#login`。

`UserService.java:66-104` 的步骤：

1. 按 `username` 查 `user` 表；
2. `PasswordUtil.matches` 校验 BCrypt 密码；
3. 账号不存在或密码错误统一提示「账户或密码错误」，避免泄露账号是否存在；
4. `status == 0`（禁用）返回 403；
5. `JwtUtil.createToken(user.getId())` 生成 JWT；
6. 把 token 写入 Redis `login:user:token:{userId}`，TTL 2 小时；
7. `authService.reload(userId)` 强制回源重建鉴权快照并写缓存；
8. 返回 `Result.success(token)`。

**一个用户只保留一个有效 token**：重复登录会覆盖 Redis 中的旧 token，旧 token 即使 JWT 未过期也会被拦截器拒绝。

### 5.2 JWT 与 Redis 双保险

`util/JwtUtil.java`：

- `createToken(Long userId)`：HMAC256 签名，subject 存 userId；
- `parseToken(String token)`：验签并返回 userId；
- 读取 `jwt.secret` 与 `jwt.timeout`。

为什么要 Redis：

| 只靠 JWT | JWT + Redis |
|---|---|
| 签发后无法主动失效，除非等过期 | 登出/禁用/重置密码/被顶号时删除或覆盖 Redis token，立即失效 |
| 无法限制同一账号多端登录 | 一个用户一个 token，新登录顶掉旧登录 |

拦截器做两件事：

1. JWT 验签（签名、过期）；
2. 比对 Redis 中的当前 token。

两者都通过才算登录态有效。

### 5.3 LoginInterceptor

`config/LoginInterceptor.java`：

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    String token = resolveBearerToken(request.getHeader(HttpHeaders.AUTHORIZATION));
    if (token == null) {
        throw new BusinessException(ResultCode.UNAUTHORIZED, "未登录");
    }

    Long userId = jwtUtil.parseToken(token);
    String redisKey = LOGIN_USER_TOKEN_KEY + userId;
    String currentToken = stringRedisTemplate.opsForValue().get(redisKey);

    if (userId == null || currentToken == null || !currentToken.equals(token)) {
        throw new BusinessException(ResultCode.UNAUTHORIZED, "登录已失效,请重新登录");
    }

    UserAuth userAuth = authService.getOrLoad(userId);
    UserContext.set(userAuth);
    checkPermission(handler, userAuth);
    renewIfBelowThreshold(redisKey);
    return true;
}
```

要点：

- `resolveBearerToken` 兼容 `Bearer xxx` 与裸 token；
- 捕获 `JWTVerificationException` → 401；
- Redis 连接等运行时异常不吞，交给全局异常处理为 500；
- `afterCompletion` 必须 `UserContext.clear()`，避免线程池复用导致用户串号；
- 滑动续期采用节流：仅当剩余 TTL 小于阈值（1 小时）时才 `EXPIRE`，避免每个请求都写 Redis。

### 5.5 AuthService

`service/impl/AuthService.java`：

| 方法 | 作用 |
|---|---|
| `getOrLoad(userId)` | 缓存优先；命中则（节流）续期；未命中回源 DB 重建并写回 |
| `reload(userId)` | 绕过缓存强制回源，登录成功时调用 |
| `cache(userAuth)` | 写入 `login:user:auth:{userId}`，TTL 2 小时 |
| `evict(userId)` | 删除快照，角色/部门变更后调用 |
| `loadFromDb(userId)` | 查用户 + 角色码 + 权限码，组装 `UserAuth` |

`loadFromDb` 的顺序：

```java
User user = userMapper.selectById(userId);
if (user == null) {
    throw new BusinessException(ResultCode.UNAUTHORIZED, "登录已失效,请重新登录");
}
return new UserAuth(
    userId,
    user.getDepartmentId(),
    new HashSet<>(roleMapper.selectRoleCodesByUserId(userId)),
    new HashSet<>(permissionMapper.selectPermCodesByUserId(userId))
);
```

缓存失效时机：

- 登录成功：`reload`，保证拿到最新角色权限；
- 分配用户角色：`assignRoles` 后 `evict`；
- 调整部门：`assignDepartment` 后 `evict`；
- 分配角色权限：`assignPermissions` 后遍历该角色所有用户逐个 `evict`；
- 禁用/重置密码/删除/登出：`logoutRemote` 同时删 token 与快照。

### 5.6 RequiresPermission

`common/annotation/RequiresPermission.java`：

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RequiresPermission {
    String[] value();
}
```

拦截器中的判定：

```java
RequiresPermission required = AnnotatedElementUtils.findMergedAnnotation(
        handlerMethod.getMethod(), RequiresPermission.class);
if (required == null) {
    required = AnnotatedElementUtils.findMergedAnnotation(
            handlerMethod.getBeanType(), RequiresPermission.class);
}
if (required != null && !userAuth.hasAll(required.value())) {
    throw new BusinessException(ResultCode.FORBIDDEN, "无权限");
}
```

语义：

- 方法上的注解优先于类上的；
- 多个权限值是「全部满足」（AND），不是「任一满足」（OR）；
- 非 `HandlerMethod`（如静态资源）不校验。

因此，**当同一接口根据不同情况需要不同权限时，不能用这个注解**，应在 Service 内动态判权。项目中的两个先例：

- `POST /workorder/{id}/dispatch`：派单要 `workorder:dispatch`，转派要 `workorder:transfer`；
- `PUT /tool/workorder/{id}/status`：按目标动作分别需要 review / dispatch / process / accept / withdraw 之一（当前为演示实现）。

### 5.10 登出、禁用与顶号

`UserService#logoutRemote`（`UserService.java:591-596`）：

```java
private void logoutRemote(Long userId) {
    stringRedisTemplate.delete(LOGIN_USER_TOKEN_KEY + userId); // 删 token
    authService.evict(userId);                                // 删鉴权快照
}
```

触发场景：

- 用户主动登出；
- 管理员禁用账号（`status=0`）；
- 管理员重置密码；
- 管理员删除用户；
- 用户重新登录（覆盖 token）。

「顶号」：登录时直接覆盖 Redis token，旧 token 与新 token 不相等，拦截器拒绝旧 token。

### 5.11 密码安全

`util/PasswordUtil.java`：

- 使用 `BCryptPasswordEncoder`，强度来自 `password.bcrypt.strength`（默认 10）；
- `encode` 拒绝空密码与超过 72 字节的 UTF-8 密码（BCrypt 的输入上限）；
- `matches` 对空值返回 false；
- 数据库中存 60 字符 BCrypt 哈希，明文永不落库。

### 6.2 实体注解

以 `model/pojo/WorkOrder.java` 为例：

```java
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
@TableName("work_order")
public class WorkOrder {

    @TableId(type = IdType.AUTO)
    private Long id;

    private String orderNo;
    private Long userId;
    private Long departmentId;
    private Long handlerId;
    private String title;
    private String content;
    private Integer orderType;
    private Integer priority;
    private Integer status;
    private String remark;
    private LocalDateTime createTime;
    private LocalDateTime updateTime;
    private LocalDateTime expireTime;

    @Version
    private Integer version;

    @TableLogic
    private Integer deleted;
}
```

| 注解 | 作用 |
|---|---|
| `@TableName` | 指定表名；`user` 是 MySQL 保留字，故 `User` 写成 ``@TableName("`user`")`` |
| `@TableId(type = IdType.AUTO)` | 主键自增 |
| `@TableLogic` | 逻辑删除字段，MP 生成的查询自动追加 `deleted = 0` |
| `@Version` | 乐观锁字段，配合 `OptimisticLockerInnerInterceptor` |
| `@Data` / `@Builder` / 构造器注解 | Lombok 生成 getter/setter/builder |
| `@Schema` | Knife4j/OpenAPI 字段说明 |

其他实体（`Department`、`Role`、`Permission`、`Notification` 等）同样使用这套注解；记录型表（日志、通知、outbox）没有 `deleted` / `version`。

### 6.3 POJO、DTO、VO

| 类型 | 位置 | 作用 | 示例 |
|---|---|---|---|
| POJO | `model/pojo` | 数据库映射 | `WorkOrder` 含 `version`、`deleted` |
| DTO | `model/dto` | 接收请求 | `WorkOrderCreateDTO` 不含 `userId`、`status` |
| VO | `model/vo` | 返回响应 | `WorkOrderVO` 不含 `content`、`version`、`deleted`；`WorkOrderDetailVO` 含资源与日志 |

典型转换：


- 防止前端传 `userId` 伪造提单人；
- 防止返回密码、逻辑删除标记等内部字段；
- DTO 上可挂校验注解，VO 上可挂展示描述；
- 接口契约变化不影响数据库模型。

### 6.5 MyBatis-Plus 用法

#### BaseMapper

所有 Mapper 继承 `BaseMapper<T>`，直接获得：

- `insert`、`deleteById`、`updateById`、`selectById`；
- `selectList`、`selectOne`、`selectCount`、`selectPage`。

#### LambdaQueryWrapper

```java
LambdaQueryWrapper<User> wrapper = new LambdaQueryWrapper<User>()
        .orderByAsc(User::getId);

if (StringUtils.hasText(keyword)) {
    wrapper.and(w -> w.like(User::getUsername, keyword)
            .or().like(User::getRealName, keyword));
}
```

要点：

- 用方法引用而非字符串列名，改名有编译期保护；
- OR 条件必须用 `and(w -> ...)` 包成一组，避免把逻辑删除等其它条件「或」掉；
- `selectPage(new Page<>(current, size), wrapper)` 才会真正分页（依赖分页插件）。

#### 手写 SQL

`UserMapper#selectUserIdsByDepartmentAndRole`：

```java
@Select("SELECT u.id FROM `user` u "
        + "JOIN user_role ur ON ur.user_id = u.id "
        + "JOIN `role` r ON r.id = ur.role_id "
        + "WHERE u.department_id = #{departmentId} "
        + "AND r.role_code = #{roleCode} "
        + "AND u.status = 1 AND u.deleted = 0")
List<Long> selectUserIdsByDepartmentAndRole(...);
```

**关键坑：`@TableLogic` 只对 MP 生成的 SQL 生效，手写 `@Select` 必须自己写 `deleted = 0`。**

`WorkOrderMapper#countActiveResourceApplications` 同理，手写了 `w.deleted = 0`。

#### 幂等插入

`NotificationMapper#insertIgnoreDuplicate`：

```java
@Insert("INSERT INTO notification (...) VALUES (...) "
        + "ON DUPLICATE KEY UPDATE id = id")
int insertIgnoreDuplicate(Notification notification);
```

返回值：

- 1 = 新插入；
- 0 = 撞唯一键，重复消息，跳过。

为什么不用 `INSERT IGNORE`：它会忽略所有错误（包括 NOT NULL 违规），导致通知静默丢失。
为什么不用 `catch (DuplicateKeyException)`：在事务中会把事务标记为 rollback-only，污染同批其他收件人。

#### N+1 避免

`UserService#pageUsers` 装配部门名与角色时：

1. 一次查当前页所有用户；
2. 一次查这些用户的 `user_role`；
3. 一次查角色码；
4. 内存分组拼装。

查询次数与页大小无关，避免逐用户查库。

### 6.6 索引与约束设计

### 6.7 逻辑删除与乐观锁

#### 逻辑删除

`User` 与 `WorkOrder` 带 `@TableLogic deleted`：

- MP 生成的 `selectById`、`selectList`、`selectCount` 自动追加 `deleted = 0`；
- `deleteById` 实际执行 `UPDATE deleted = 1`；
- 手写 SQL 必须手动加 `deleted = 0`。

`UserService#deleteUser` 还额外物理删除 `user_role` 关联，避免残留脏授权。

#### 乐观锁

```java
@Version
private Integer version;
```

更新链路：

1. 从库中读出实体（含当前 `version`）；
2. 修改字段；
3. `updateById(entity)`；
4. MP 自动追加 `WHERE id = ? AND version = 旧值`，成功后 `version + 1`；
5. 影响行数为 0 说明版本已被别人改过，业务层抛 409。

`WorkOrderService#transition` 中的判定：

```java
if (workOrderMapper.updateById(order) == 0) {
    throw new BusinessException(ResultCode.CONFLICT, "工单已被他人修改,请刷新后重试");
}
```

### 7.4 transition 通用流转

`WorkOrderService#transition`（`WorkOrderService.java:546-586`）是所有状态变更的唯一汇聚点：

```java
private void transition(WorkOrder order, WorkOrderStatus target, OperateType operateType,
                        Long toUserId, String remark, Consumer<WorkOrder> mutator) {
    WorkOrderStatus current = WorkOrderStatus.fromCode(order.getStatus());

    // 1. 状态机校验
    if (!current.canTransitionTo(target)) {
        throw new BusinessException(ResultCode.CONFLICT,
                "当前状态[" + current.getDesc() + "]不允许该操作");
    }

    // 2. 修改状态 / 处理人 / 备注 / 调用方附加字段
    order.setStatus(target.getCode());
    if (toUserId != null) order.setHandlerId(toUserId);
    if (remark != null) order.setRemark(remark);
    if (mutator != null) mutator.accept(order);

    // 3. 显式刷新 update_time
    order.setUpdateTime(LocalDateTime.now());

    // 4. 乐观锁更新
    if (workOrderMapper.updateById(order) == 0) {
        throw new BusinessException(ResultCode.CONFLICT, "工单已被他人修改,请刷新后重试");
    }

    // 5. 事务提交后删缓存
    cacheClient.evictAfterCommit(RedisConstants.WORKORDER_DETAIL_KEY + order.getId());

    // 6. 写操作日志
    insertLog(order.getId(), UserContext.getUserId(), operateType,
            current.getCode(), target.getCode(), toUserId, remark);

    // 7. 写通知意图(必须在状态/处理人更新之后)
    notifyOutboxWriter.stage(NotifyMessage.of(
            order.getId(), order.getOrderNo(), order.getTitle(),
            order.getDepartmentId(), order.getUserId(), order.getHandlerId(),
            UserContext.getUserId(), operateType,
            current.getCode(), target.getCode(), remark));
}
```

两个重载：

- 5 参数版本：只改状态/处理人/备注；
- 6 参数版本：额外接受 `Consumer<WorkOrder> mutator`，用于「重提时同时修改标题/描述」这类「状态 + 内容」一次更新。

为什么显式 `setUpdateTime`：`updateById` 会把实体读取时的旧 `updateTime` 写回，覆盖 MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`。

### 7.5 创建工单

`WorkOrderService#create`（`WorkOrderService.java:143-159`）**刻意不加 `@Transactional`**：

```java
@Override
public Long create(WorkOrderCreateDTO dto) {
    Long departmentId = UserContext.getDepartmentId();
    if (departmentId == null) {
        throw new BusinessException(ResultCode.BAD_REQUEST, "当前用户未归属部门,无法提交工单");
    }

    if (isResourceApply(dto)) {
        List<String> lockKeys = resourceLockKeys(distinctResourceKeys(dto), departmentId);
        return redisLockHelper.executeWithMultiLock(lockKeys,
                lockProperties.getResourceWaitSeconds(), lockProperties.getResourceLeaseSeconds(),
                () -> transactionTemplate.execute(status -> doCreate(dto, departmentId)));
    }

    return transactionTemplate.execute(status -> doCreate(dto, departmentId));
}
```

为什么用 `TransactionTemplate` 而不是 `@Transactional`：

- 如果锁在 `@Transactional` 方法内部，方法返回时事务尚未提交，锁就先释放了；
- 下一个并发请求会在前一个事务未提交时通过校验，互斥形同虚设；
- 用编程式事务把「数据库写入」包成一个显式事务，让锁的生命周期 ≥ 事务生命周期。

`doCreate`（`WorkOrderService.java:169-217`）：

1. 资源申请（`orderType=2` 且有明细）时，在锁内逐资源调用 `countActiveResourceApplications`，同部门已有进行中的同类申请则 409；
2. 从 `UserContext` 取 `userId` / `departmentId`，不信任前端；
3. 生成工单编号；
4. 插入主表：初始状态 0，`expireTime` 默认当前 + 72 小时；
5. 插入资源明细；
6. 写操作日志（`fromStatus = null`）；
7. `notifyOutboxWriter.stage(...)` 写通知意图。

资源申请互斥的锁 key：

```
lock:resource:apply:{departmentId}:{resourceType}:{resourceName}
```

同一张单多个资源会生成多把锁，由 `executeWithMultiLock` 去重 + 字典序排序，防死锁。

「进行中」的判定（`WorkOrderMapper#countActiveResourceApplications`）：

```sql
w.order_type = 2
AND w.status IN (0, 1, 2, 3, 5)
AND w.deleted = 0
```

已完成/已取消/已超时后允许再次申请。

### 7.6 重新提交

`WorkOrderService#resubmit`（`WorkOrderService.java:226-263`）：

1. `requireOrder` + `requireSubmitterSelf`；
2. 调用 `transition` 走 `5 → 0`，同时通过 `mutator` 修改标题/描述/类型/优先级；
3. 超时时间只有传了才重置，否则沿用原值；
4. 资源明细传了就「删除旧明细 + 插入新明细」；
5. 因为明细被替换，**再删一次详情缓存**。

第 5 步的原因：`transition` 已注册一次缓存失效，但那次失效发生在「明细尚未替换」的时刻；如果只删一次，异步重建可能读到「新主表 + 旧明细」的组合。两次 `evictAfterCommit` 覆盖这个窗口。

### 7.7 列表与统计

`page`（`WorkOrderService.java:269-280`）：

```java

if (status != null) wrapper.eq(WorkOrder::getStatus, status);
wrapper.orderByDesc(WorkOrder::getCreateTime);
```

`buildListWrapper`：

`WorkOrderService#closeTimeout`（`WorkOrderService.java:473-518`）：

2. 逐条校验 `canTransitionTo(TIMEOUT)`；

### 7.10 工单编号生成

```java
        });
```

格式：`WO + yyyyMMdd + 6 位日内序号`，例如 `WO20261018000001`。

要点：

- `INCR` 本身原子，编号唯一主要靠它 + `uk_order_no`；
- 锁守的是「`INCR` + 首次 `EXPIRE`」两步的原子性，防止首次生成时进程崩溃留下永不过期的序号键；
- 序号 key TTL 2 天，跨天自然换新 key；
- 编号只要唯一、不要求连续，抢锁失败/事务回滚造成的空洞可接受。

### 7.11 操作日志

`WorkOrderService#insertLog`：

```java
workOrderOperateLogMapper.insert(WorkOrderOperateLog.builder()
        .orderId(orderId)
        .operatorId(operatorId)
        .operateType(operateType.getCode())
        .fromStatus(fromStatus)
        .toStatus(toStatus)
        .toUserId(toUserId)
        .remark(remark)
        .build());
```

记录内容：

- 谁（`operator_id`，系统操作为 0）；
- 做了什么（`operate_type`）；
- 从哪个状态到哪个状态（`from_status` / `to_status`）；
- 目标处理人（派单/转派时）；
- 备注。

日志表只增不改，用于审计与问题追溯。

## 8. Redis 使用场景

### 8.1 key 总表

| key 模式 | 值 | TTL | 失效方式 | 用途 |
|---|---|---|---|---|
| `login:user:token:{userId}` | JWT 字符串 | 2h（滑动续期） | 登出/禁用/顶号删除或覆盖 | 当前有效登录态 |
| `login:user:auth:{userId}` | `UserAuth` JSON | 2h（滑动续期） | 角色/部门变更后 DEL | 鉴权快照 |
| `workorder:no:seq:{yyyyMMdd}` | 整数 | 2 天 | 自然过期 | 日内编号序列 |
| `notify:unread:{userId}` | 未读数字符串 | 300s | 新增通知/标记已读后 DEL | 未读数缓存 |
| `workorder:detail:{id}` | `RedisData<WorkOrderDetailVO>` | 逻辑 300s / 物理 1800s | 状态变更后 DEL + 逻辑过期重建 | 工单详情 |
| `workorder:absent:{id}` | `"1"` | 60s | 自然过期 | 空值哨兵防穿透 |
| `permission:tree` | `List<PermissionVO>` | 1800s | TTL-only | 权限树字典 |
| `role:perms:{roleId}` | `List<Long>` | 600s | 分配权限后 DEL + TTL | 角色已分配权限 |
| `lock:workorder:no` | Redisson 锁 | lease 5s | 自动释放 | 编号生成临界区 |
| `lock:resource:apply:{dept}:{type}:{name}` | Redisson MultiLock | lease 10s | 自动释放 | 资源申请互斥 |
| `lock:cache:{业务key}` | Redisson 锁 | lease 5s | 自动释放 | 缓存重建互斥 |

常量集中定义在 `common/RedisConstants.java` 与 `common/LockConstants.java`。

### 8.2 登录态

- 登录写入 token，TTL 2 小时；
- 每次请求先验 JWT，再比对 Redis token；
- 剩余 TTL 低于 1 小时才续期，避免每请求 EXPIRE；
- 登出/禁用/重置密码/删除用户/重新登录都会让旧 token 失效。

### 8.3 鉴权快照

登录后把「部门 + 角色码 + 权限码」组装成 `UserAuth` 写入 Redis：

- 后续请求零 DB 查询；
- 角色/部门/权限变更时主动删除快照；
- 快照与 token 同 TTL，避免「token 还有效但权限数据过期」。

### 8.4 工单编号序列

`StringRedisTemplate.opsForValue().increment(seqKey)`：

- 原子自增；
- 首次写入补 2 天 TTL；
- 在 Redisson 锁内执行，保证「INCR + EXPIRE」原子。

为什么不用数据库自增：编号需要「按天重置 + 可读格式」，数据库自增无法按天归零，且会暴露总量。

### 8.5 未读数缓存

`NotificationService#unreadCount`（`NotificationService.java:113-134`）：

1. 读 `notify:unread:{userId}`；
2. 命中且能解析为数字 → 直接返回；
3. 值非法 → 删除后回源；
4. 未命中 → `selectCount` 统计未读，写回，TTL 300s。

失效策略是「写失效 + TTL 兜底」，不用 `INCR`：

- `DEL` 幂等，不会算错；
- 最坏只是下次读回源一次（索引覆盖计数）；
- 新增通知实际插入 > 0 行时，对该批收件人逐个 DEL；
- 标记已读/全部已读后 DEL 自己。

### 8.6 工单详情缓存

`CacheClient#getLogical`（`cache/CacheClient.java:133-154`）流程：

1. **先查空值哨兵**：存在 → 直接返回 null，不打 DB；
2. **读逻辑过期包装** `RedisData`：
   - 未过期 → 返回 `data`；
   - 已过期 → **立即返回旧值**，提交异步重建；
3. **未命中** → 同步互斥重建。

`RedisData`：

```java
public class RedisData<T> {
    private T data;
    private long expireAtEpochMilli;   // 逻辑过期时间
}
```

重建：

- 抢 `lock:cache:{key}`；
- 抢到：二次检查 → 回源 → 回填；
- 抢不到：不阻塞，直接回源 DB。

回源结果：

- 有值 → 写 `RedisData`，物理 TTL 1800s；
- 为 null → 写 `workorder:absent:{id}`，TTL 60s。

为什么物理 TTL 必须大于逻辑 TTL：物理 TTL 只是兜底清场；若物理先到期，逻辑过期机制就名存实亡，读路径退化成同步重建。

`getOrLoad`（普通 TTL 缓存）用于权限树与角色权限：

```java
T value = cacheClient.getOrLoad(key, ttl, loader);
```

未命中时也有互斥重建，但值直接存，不包 `RedisData`。

### 8.7 字典缓存

| 数据 | 策略 | 原因 |
|---|---|---|
| 权限树 | TTL-only，30 分钟 | 当前系统没有增删权限接口，字典几乎不变 |
| 角色已分配权限 | 写失效为主 + TTL 10 分钟 | 会随「分配权限」变化，必须先删缓存 |

### 8.8 缓存三大问题

| 问题 | 项目中的处理 |
|---|---|
| **穿透**（查不存在的数据） | 空值哨兵 `workorder:absent:{id}`，TTL 60s；同时先校验 ID 合法性 |
| **击穿**（热点 key 失效瞬间大量请求打 DB） | 互斥重建：未命中抢锁，抢到回源，抢不到直接回源（不排队）；逻辑过期让读请求不阻塞 |
| **雪崩**（大量 key 同时过期） | 逻辑过期 + TTL 分散；缓存重建线程池满时丢弃任务，不拖垮请求线程 |

### 8.9 分布式锁

`lock/RedisLockHelper.java` 封装 Redisson：

| 方法 | 行为 |
|---|---|
| `tryLock(key, wait, lease)` | 显式等待 + 显式租约；中断抛 500 |
| `unlock(key)` | 仅当前线程持有才释放；释放异常记 warn，由租约自愈 |
| `executeWithLock(...)` | 拿不到锁抛 409「操作过于频繁」 |
| `executeWithMultiLock(...)` | 去重 + 字典序排序，防死锁；拿不到全部锁抛 409 |

三条纪律：

1. **显式租约**：不用无参 `lock()`，关闭看门狗自动续约；
2. **持有者才能释放**：`isHeldByCurrentThread()`；
3. **写路径拿不到锁不降级**：直接 409，绝不无锁执行。

唯一例外是缓存重建：拿不到锁退化为「直接回源 DB」，因为它是读优化，不能影响可用性。

### 8.10 序列化

- `RedisTemplate<String, Object>`：key 用字符串，value 用 Jackson 3 JSON + `@class` 类型信息；
- `RedisData`、`UserAuth`、VO 都能正确还原；
- Redisson 只用 `StringCodec`，与 Jackson 缓存数据不重叠；
- 所以项目里同时存在「Jackson 3 缓存」与「Redisson 字符串锁」两套序列化，但永不相遇。

## 9. RabbitMQ 异步通知

### 9.1 为什么异步

工单流转通知不是主流程的必要条件：

- 同步发通知会拉长接口响应；
- broker 故障不应该让工单提交失败；
- 通知失败需要重试，不能阻塞请求线程。

因此采用「本地消息表 + 异步投递」：

- 业务事务内只写 outbox 表；
- 事务提交后再发 MQ；
- 发送失败由补偿任务重投；
- 消费端幂等落库。

### 9.2 三段式可靠性

| 段 | 组件 | 解决的问题 |
|---|---|---|
| 第一段：意图落库 | `NotifyOutboxWriter` | 消息发出但事务回滚 → 幽灵通知 |
| 第二段：提交后发送 | `NotifyMessagePublisher` | 事务未提交就发消息 / 多实例重复发送 |
| 第三段：补偿重投 | `MqCompensationJob` | 发送失败、进程崩溃、确认丢失 |

### 9.3 消息流转

```
业务事务
   │
   ├─ 写 work_order / log
   └─ NotifyOutboxWriter.stage(...)
          ├─ 序列化 NotifyMessage → msg_body
          ├─ INSERT mq_message_reliability(status=0)
          └─ publishEvent(WorkOrderNotifyEvent)
                    │
                    │ 事务提交后
                    ▼
        NotifyMessagePublisher.onNotifyEvent
          (@TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true))
          (@Transactional(REQUIRES_NEW))
                    │
                    ├─ claim:CAS status 0 → 1 + 发送租约
                    ├─ publishBatch:rabbitTemplate.invoke 批量发送
                    ├─ 等 confirm(3s)
                    └─ markSuccess(status=2)/ markFailure(退避或 status=3)
                    │
                    ▼
             RabbitMQ topic exchange
                    │ workorder.notify.#
                    ▼
             workorder.notify.queue
                    │ 手动 ACK
                    ▼
        NotifyMessageConsumer.onMessage
                    ├─ 解析 NotifyMessage
                    ├─ NotifyDispatcher.resolveRecipients
                    ├─ NotificationService.saveIfAbsent(幂等)
                    └─ basicAck
                    │
                    ▼
              notification 表
```

### 9.4 关键类

| 类 | 职责 |
|---|---|
| `mq/NotifyMessage` | 事件载荷；生产/消费共用 `jsonMapper()` |
| `mq/WorkOrderNotifyEvent` | 应用事件，携带一批 outbox 行 |
| `mq/NotifyOutboxWriter` | 事务内落 outbox + 发应用事件 |
| `mq/NotifyMessagePublisher` | AFTER_COMMIT 认领、发送、确认、回写终态 |
| `mq/NotifyMessageConsumer` | 手动 ACK 消费、幂等落库 |
| `service/impl/NotifyDispatcher` | 收件人规则 + 文案模板 |
| `service/impl/NotificationService` | 通知落库、分页、未读数、已读 |
| `job/MqCompensationJob` | 孤儿回收 + 待发扫描 + 重投 |

### 9.5 事务边界

`NotifyOutboxWriter#stage` 的三条自我约束（`mq/NotifyOutboxWriter.java:15-29`）：

1. **不发送**：事务未提交，发出去可能是幽灵通知；
2. **不 try-catch**：INSERT 失败必须让工单事务回滚，否则工单建好了却没有通知；
3. **不门控**：`mq.notify.enabled=false` 时 outbox 照写（停在 status=0），工单业务不因本机没 broker 改变行为。

`NotifyMessagePublisher#onNotifyEvent`：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public void onNotifyEvent(WorkOrderNotifyEvent event) { ... }
```

为什么 `REQUIRES_NEW`：AFTER_COMMIT 阶段，已提交事务的连接仍绑定在当前线程上，直接写库会写进已结束的事务，连接归还时被回滚，回写会静默丢失。必须另起事务。

### 9.6 确认与失败处理

`publishBatch`（`mq/NotifyMessagePublisher.java:134-160`）：

- 用 `rabbitTemplate.invoke(operations -> ...)` 让整批共用一个 Channel；
- 每条消息带 `CorrelationData(msgId)`；
- 发送后逐条等 confirm（最多 3 秒）；
- `confirm.ack()` 为 false → 失败；
- `correlationData.getReturned() != null` → 交换机存在但路由不到队列，同样按失败处理。

失败处理 `markFailure`：

- `retry_count + 1`；
- 未耗尽 → `status=0`，`next_retry_time = now + 30s`；
- 耗尽（`retry_count >= maxRetry`）→ `status=3`，等待人工介入。

为什么要在此收口 status=3：补偿任务只扫 `status=0 且 retry_count < maxRetry`，若不在这里改成终态，失败记录会永远停在 0 却再也扫不到。

### 9.7 消费与幂等

`NotifyMessageConsumer`：

- `@RabbitListener(queues = "${mq.notify.queue:workorder.notify.queue}")`；
- 手动 ACK；
- 参数是原始 `Message`，自行用 `NotifyMessage.fromJson` 反序列化；
- 收件人为空 → `basicAck` + warn（合法结果，不是失败）；
- 落库成功 → `basicAck`；
- 解析/写入异常 → 故意不捕获，交给容器重试 → 重试耗尽进 DLQ。

幂等做在存储层：

```sql
UNIQUE KEY uk_msg_user (msg_id, user_id)
ON DUPLICATE KEY UPDATE id = id
```

同一消息对同一收件人只会有一行；重复消费影响行数为 0，照常 ACK。

### 9.8 收件人解析

`NotifyDispatcher#resolveRecipients`：

| 事件 | 收件人 |
|---|---|
| `SUBMIT` | 本部门 `REVIEWER` |
| `REVIEW_PASS` | 本部门 `DISPATCHER` |
| `REVIEW_REJECT` | 提单人 |
| `DISPATCH` | 新处理人 |
| `PROCESS_FINISH` | 提单人 |
| `ACCEPT_PASS` | 处理人 |
| `ACCEPT_REJECT` | 处理人 |
| `TRANSFER` | 新处理人（不通知原处理人） |
| `WITHDRAW` | 有处理人 → 处理人；否则本部门 `DISPATCHER` |
| `TIMEOUT_CLOSE` | 提单人 + 处理人 |

两条贯穿规则：

1. **永远排除操作人自己**；
2. **转派不通知原处理人**（刻意的产品判断）。

收件人为空是合法结果，消费端必须 ACK。

### 9.9 补偿任务

`job/MqCompensationJob.java`：

```java
@Scheduled(fixedDelayString = "${mq.notify.compensation.scan-delay-ms:30000}")
public void compensate() { ... }
```

每轮两件事：

1. **回收孤儿**：`status=1 且 next_retry_time <= NOW()` → 复位为 0。
   - 认领时会把 `next_retry_time` 推到「现在 + send-lease(30s)」；
   - 在途消息的 `next_retry_time` 在未来，不会被误伤；
   - 只有超出租约仍未结算的行才复位。
2. **扫描待发**：`status=0`、`next_retry_time <= NOW()`、`retry_count < maxRetry`、`LIMIT batchSize`；
   - CAS 认领；
   - 走同一个 `publishBatch`，保证与「提交后发送」行为一致。

稳态下扫不到任何数据，零写入。这是降级路径，不是常态路径。

### 9.10 配置与降级

- `mq.notify.enabled=true`：注册 MQ 拓扑、publisher、consumer、补偿任务；
- `mq.notify.enabled=false`：
  - `RabbitMqConfig`、`NotifyMessagePublisher`、`NotifyMessageConsumer`、`MqCompensationJob` 都不创建；
  - `NotifyOutboxWriter` 仍写 outbox（status=0）；
  - 应用可正常启动，工单业务不受影响。

消费端重试配置（application.yaml）：

- 手动 ACK；
- prefetch 10；
- 并发 2～4；
- 重试 3 次，初始 1s，倍数 2，最大 10s；
- 重试耗尽不 requeue，交给 DLX → DLQ。

### 10.4 派单与转派

同一个接口 `POST /workorder/{id}/dispatch`，按当前状态分流：

```java
WorkOrder order = requireOrder(id);
requireHandlerExists(dto.getHandlerId());

WorkOrderStatus current = WorkOrderStatus.fromCode(order.getStatus());
if (current == WorkOrderStatus.PENDING_DISPATCH) {
    requirePermission("workorder:dispatch");
    requireDepartmentScope(order);
    transition(order, PROCESSING, DISPATCH, handlerId, remark);
} else if (current == WorkOrderStatus.PROCESSING) {
    requirePermission("workorder:transfer");
    requireTransferScope(order);
    transition(order, PROCESSING, TRANSFER, handlerId, remark);
} else {
    throw new BusinessException(CONFLICT, "当前状态[...]不允许派单/转派");
}
```

`transition` 内：

- 状态机校验 `1→2` 或 `2→2`；
- 设置 `status` / `handlerId` / `remark`；
- 乐观锁更新；
- 删详情缓存（提交后）；
- 写操作日志；
- 写通知意图（此时 `handlerId` 已是新处理人，收件人正确）。

Controller 上**没有** `@RequiresPermission`，原因见 5.6。

### 10.5 通知异步链路

以派单为例：

1. `transition` 调用 `notifyOutboxWriter.stage(NotifyMessage.of(...))`：
   - `operateType = DISPATCH`；
   - `handlerId = 新处理人`；
   - `operatorId = 当前派单人`；
2. `stage`：
   - `message.toJson()` 得到 `msg_body`；
   - 插入 `mq_message_reliability`，`status=0`，`next_retry_time=now`；
   - `publishEvent(new WorkOrderNotifyEvent(rows))`；
3. 工单事务提交；
4. `NotifyMessagePublisher#onNotifyEvent`：
   - `claim`：CAS `status 0→1`，`send_time=NOW()`，`next_retry_time=NOW()+30s`；
   - `publishBatch`：
     - `rabbitTemplate.invoke` 批量发送；
     - routing key = `workorder.notify.dispatch`；
     - 等 confirm；
     - 成功 `status=2`，失败退避或 `status=3`；
5. RabbitMQ 路由到 `workorder.notify.queue`；
6. `NotifyMessageConsumer#onMessage`：
   - 解析 `NotifyMessage`；
   - `NotifyDispatcher#resolveRecipients` → 新处理人；
   - `NotificationService#saveIfAbsent`：
     - 渲染文案；
     - 逐收件人 `insertIgnoreDuplicate`；
     - 插入成功 > 0 时删未读缓存；
   - `basicAck`；
7. 处理人查询 `GET /notification/unread-count` 看到红点。

## 12. 开发规范与最佳实践

### 12.1 新增一个接口的步骤

以「新增一个工单动作」为例：

1. **DTO**：在 `model/dto` 建请求对象，加 `@NotBlank` / `@NotNull` 等校验；
2. **VO**：如需返回数据，在 `model/vo` 建视图对象，不暴露内部字段；
3. **Service 接口**：在 `IWorkOrderService` 声明方法；
4. **Service 实现**：
   - 从 `UserContext` 取当前用户，不从请求参数取；
   - 做数据范围/本人校验；
   - 状态变更走 `transition`；
   - 写操作日志；
   - 写通知意图；
   - 需要事务时加 `@Transactional(rollbackFor = Exception.class)`；
   - 需要缓存失效时用 `cacheClient.evictAfterCommit`；
5. **Controller**：加路由、`@Valid`、`@RequiresPermission`，把结果包成 `Result`；
6. **权限数据**：如需新权限码，更新 `data.sql` 的 `permission` 与 `role_permission`，并通知所有用户重新登录或主动清快照；
7. **文档**：`@Tag` / `@Operation`；
8. **验证**：正常路径、越权、非法状态、并发（乐观锁）、缓存命中/失效。

### 12.2 分层规范

- Controller 不写业务判断，不直接调 Mapper；
- Service 不处理 HTTP 细节；
- Mapper 只做数据访问；
- DTO 不包含 `userId`、`status`、`version`、`deleted` 等应由服务端决定的字段；
- VO 不返回密码、逻辑删除标记、内部版本号；
- 公共常量放 `common`，不散落魔法值。

### 12.3 事务规范

- 单次数据库写入用 `@Transactional(rollbackFor = Exception.class)`；
- 需要「锁包住事务」时用 `TransactionTemplate`，不要给方法加 `@Transactional`（见 `WorkOrderService#create`）；
- 缓存删除用 `evictAfterCommit`，不要事务内直接删；
- MQ 发送在 `AFTER_COMMIT`，回写用 `REQUIRES_NEW`；
- 不要把远程调用、MQ 发送放在数据库事务内。

### 12.4 缓存规范

- 读走 `CacheClient`，业务层不直接碰 `RedisTemplate`（登录态/未读数等简单场景除外）；
- 写路径「先改库、提交后删缓存」，不更新缓存；
- 热点详情用「逻辑过期 + 异步重建」；
- 不存在的数据写短 TTL 空值哨兵；
- 缓存异常吞掉记 warn，退化为回源 DB；
- TTL、线程池等参数放配置，不写死。

### 12.5 锁规范

- 锁 key 统一放 `LockConstants`；
- 一律显式 `tryLock(wait, lease)`；
- 释放前 `isHeldByCurrentThread`；
- 多资源锁去重 + 排序；
- 写路径拿不到锁直接 409，不降级；
- 锁的生命周期必须覆盖事务生命周期；
- 缓存重建锁是唯一允许「拿不到就回源」的例外。

### 12.6 MQ 规范

- 业务事务内只写 outbox，不直接发消息；
- outbox 写入失败要让业务事务回滚；
- 发送在 AFTER_COMMIT，回写用新事务；
- 消费端幂等做在存储层（唯一键），不依赖应用记忆；
- 「查出来是空」是成功，要 ACK；「没查成」才是失败，要抛异常；
- 失败重试要收口，不能留下永远扫不到的记录；
- 消费端自行反序列化，生产/消费共用同一个 mapper。

### 12.7 SQL 规范

- 手写 SQL 必须自己加 `deleted = 0`；
- 分页必须有稳定排序（本项目用 `id` 或 `create_time`）；
- 关键字模糊查询用 `and(w -> ...or...)` 包组；
- 列表查询避免 N+1，批量查回内存装配；
- 索引按查询形态设计，联合索引注意列序；
- 不用物理外键，靠索引 + 业务校验。

### 12.8 安全规范

- 用户身份只从 `UserContext` 取；
- 返回前做数据范围校验，缓存命中也不能跳过；
- 登录失败统一提示，避免账号枚举；
- 通知不存在/不属于自己统一 404，避免存在性泄漏；
- 密码只存 BCrypt 哈希；
- 管理操作禁止对自己执行（禁用/删除）；
- Tool 接口限制 `size` 上限，防止撑爆大模型上下文。

### 12.9 易错点清单

| 易错点 | 说明 |
|---|---|
| `@TableLogic` 对手写 SQL 不生效 | `@Select` 里必须手写 `deleted = 0` |
| `updateById` 默认忽略 null 字段 | 项目利用这一点做「只更新传入字段」；想清空字符串要传 `""` |
| `updateById` 会把旧 `updateTime` 写回 | `transition` 显式 `setUpdateTime(now)`，否则覆盖数据库 `ON UPDATE` |
| 缓存命中就跳过鉴权 | 错误；本项目命中缓存仍执行 `requireViewScope` |
| 锁放在事务内 | 锁先于事务提交释放，互斥失效；用 `TransactionTemplate` |
| AFTER_COMMIT 里用当前事务写库 | 回写会静默丢失；必须 `REQUIRES_NEW` |
| 消费端把空收件人当失败 | 会制造无解死信；空集应 ACK |
| 消费端吞异常并 ACK | 消息永久丢失；应抛异常走重试/DLQ |
| `@RequiresPermission` 是 AND 语义 | 需要「任一权限」时必须在 Service 动态判权 |
| 重提只删一次详情缓存 | 资源替换后要再删一次，避免读到旧明细 |
| 通知在状态更新前构造 | 派单/转派会通知到旧处理人；必须在 `transition` 更新后取 `handlerId` |
| 分页插件未注册 | `selectPage` 退化为全表查询 |
| Redis 序列化用错 Jackson 版本 | Boot 4 是 Jackson 3（`tools.jackson`），不是 Jackson 2 |
| Redisson 用 starter | 可能接管 `RedisTemplate` 或版本不匹配；本项目只用核心包 |
| 手写 `RabbitTemplate` | 会丢掉 confirm/return/mandatory 配置 |
| 路径参数校验不生效 | 类上要加 `@Validated`，参数上才生效 |
| 逻辑删除与唯一索引冲突 | `user.username` 唯一索引包含已逻辑删除行，重新注册同名账号可能撞库（当前代码只查未删除行） |

### 12.10 待改进点

以下是从当前代码中能直接看到的小问题，记录以便后续维护：

1. **Service 返回类型不一致**：`IUserService#login/register` 返回 `Result<T>`，其他方法返回领域对象/void。建议统一为 Service 返回业务对象，Controller 包 `Result`。
2. **OpenApiConfig 的 Agent Tool 分组路径不匹配**：`pathsToMatch("/AgentTool/**")` 与实际 `/tool/**` 不一致，group 名也与「通知中心」重复。
3. **逻辑删除 + 唯一索引**：`user.username` 只有普通唯一索引，逻辑删除后同名账号无法重新注册，且当前 `selectCount` 会过滤已删除行，可能先通过业务校验再撞数据库唯一键。若需要支持「删除后复用账号」，可把唯一键改为 `(username, deleted)` 或在删除时改写用户名。
4. **`work_order_attachment` 暂无接口**：表、实体、Mapper 已存在，上传/下载能力尚未实现。
5. **Tool 写接口为演示实现**：`PUT /tool/workorder/{id}/status` 只解析状态机合法性，不落库；扩展点注释已写在 `ToolWorkOrderService#changeStatus`。

## 13. 复盘问答

### Q1：为什么 HTTP 状态码统一 200，业务码放响应体？

项目约定前端只解析 `Result.code`，避免 HTTP 状态码与业务语义两套判断。代价是不能直接利用 HTTP 缓存/网关策略。见 `Result`、`GlobalExceptionHandler`。

### Q2：JWT 已经能验签和过期，为什么还要 Redis 存 token？

JWT 无法主动失效。登出、禁用、重置密码、被顶号都需要「立即失效」，所以 Redis 中的当前 token 才是真正的登录态。JWT 只保证签名与过期，Redis 负责「是否仍有效」。

### Q3：为什么一个用户只保留一个 token？

登录时直接覆盖 Redis 中的 token，实现单端登录/顶号。旧 token 与新 token 不相等，拦截器拒绝。

### Q4：鉴权快照缓存了什么？什么时候失效？

`UserAuth`：userId、departmentId、roleCodes、permCodes。登录成功 `reload`；分配角色、调整部门、分配角色权限、禁用、重置密码、删除、登出时 `evict`。

### Q5：为什么详情缓存命中后还要做权限校验？

缓存只保存工单数据，不保存「谁可以看」。角色/部门可能已变化，如果命中缓存就跳过鉴权，会出现越权窗口。`detail` 在缓存之后仍调用 `requireViewScope`。

### Q6：工单状态机在哪里定义？如何防止非法流转？

`WorkOrderStatus.TRANSITIONS` 定义允许迁移；所有流转走 `WorkOrderService#transition`，先 `canTransitionTo`，非法抛 409。

### Q7：乐观锁如何生效？

`WorkOrder.version` 加 `@Version`，`MybatisPlusConfig` 注册 `OptimisticLockerInnerInterceptor`。`updateById` 自动追加 `WHERE version = 旧值` 并 `version + 1`；影响行数 0 视为冲突。

### Q8：为什么创建工单不用 `@Transactional`？

因为资源申请需要在事务外层加分布式锁。若锁在 `@Transactional` 方法内部，方法返回时锁先释放、事务尚未提交，并发请求会穿过互斥。所以用 `TransactionTemplate` 包住落库，让锁的生命周期 ≥ 事务。

### Q9：工单编号如何保证唯一？

`WO + yyyyMMdd + Redis INCR 6 位序号`，配合 `uk_order_no` 唯一键。锁只保证「INCR + 首次 EXPIRE」原子，防首次生成时留下永不过期的 key。

### Q10：缓存穿透、击穿、雪崩分别怎么处理？

- 穿透：空值哨兵 `workorder:absent:{id}`，TTL 60s；
- 击穿：互斥重建 + 逻辑过期，读请求不阻塞；
- 雪崩：逻辑过期 + 物理 TTL 兜底 + 重建线程池丢弃策略。

### Q11：逻辑过期和普通 TTL 的区别？

普通 TTL 到期后 key 消失，读请求必须同步回源；逻辑过期把过期时间放在 value 里，key 物理上还在，读到「逻辑已过期」时先返回旧值，再异步重建。物理 TTL 只做兜底清场。

### Q12：为什么缓存删除要放在事务提交后？

事务内删除后如果事务回滚，缓存已删但数据没变，会放大无谓重建。`evictAfterCommit` 用 `TransactionSynchronizationManager` 把 DEL 挂到 `afterCommit`。

### Q13：分布式锁的三条纪律是什么？

显式租约、持有者才能释放、写路径拿不到锁不降级（直接 409）。缓存重建是唯一例外，拿不到锁直接回源。

### Q14：MultiLock 为什么要排序？

两个请求分别锁 `{A,B}` 和 `{B,A}`，不排序会互相等待死锁。`executeWithMultiLock` 对 key 去重 + 字典序排序，保证所有调用方以同一顺序获取。

### Q15：本地消息表解决什么问题？

解决「业务事务与消息发送不在同一事务」的问题。意图与业务数据在同一事务落库，回滚则意图一起消失；提交后再发送，失败由补偿任务重投。

### Q16：为什么发送监听要用 `AFTER_COMMIT` 和 `REQUIRES_NEW`？

`AFTER_COMMIT` 保证事务提交后才发，避免幽灵通知；`REQUIRES_NEW` 保证确认回写落在新事务里，否则会写进已结束的事务并静默丢失。

### Q17：消息发送成功但 confirm 丢失怎么办？

outbox 行停留在 `status=1`。补偿任务回收「租约到期仍未结算」的孤儿，复位为 `status=0` 后重投。

### Q18：消费端如何保证幂等？

`notification` 表唯一键 `(msg_id, user_id)` + `ON DUPLICATE KEY UPDATE id = id`。重复消息影响行数为 0，照常 ACK。幂等做在存储层，不依赖应用重启/并发。

### Q19：收件人为空为什么是成功？

「查出来了，结果是空的」是合法业务结果（例如部门没有在职审核人）。重试多少次结果还是空，进 DLQ 只会制造无解死信，所以应 ACK。只有解析/写入失败才是真失败。

### Q20：为什么手写 SQL 必须加 `deleted = 0`？

`@TableLogic` 只对 MyBatis-Plus 生成的 SQL 生效，`@Select` 不会被自动注入逻辑删除条件。漏写会让已删除数据参与查询，例如已删除用户收到通知。

### Q21：`@RequiresPermission` 能不能表达「任一权限」？

不能。它的语义是「全部满足」。派单/转派这种按状态需要不同权限的场景，必须在 Service 内动态判权（`requirePermission`）。

### Q22：为什么通知接口不挂权限码？

`user_id` 强制取自 `UserContext`，查询条件永远带 `id AND user_id`，结构上不可能越权。加权限码只会增加维护成本，不增加安全性。

### Q23：缓存与数据库如何保持一致？

采用 cache-aside：读走缓存，写走数据库，写后删除缓存（提交后）。不更新缓存，避免并发写导致缓存与数据库顺序错乱。

### Q24：为什么用 Redisson 核心包而不是 starter？

避免 starter 的 `spring-data-redis` 适配版本与 Boot 4 不匹配，也避免 starter 接管项目已定型的 `RedisTemplate` 序列化配置。只需要锁，不需要 Redisson 的 Spring 集成。
